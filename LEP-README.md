## ✅ Правило хранения файлов — СНЯТО 2026-07-16

**Раньше было критическим правилом:** DWG чертежа обязан лежать в той
же папке, что и модули `LEP-*.LSP` — на этом держался и поиск файлов
(`findfile`), и авторегистрация `TRUSTEDPATHS`.

**Больше не актуально.** Папка с модулями добавлена в Support File
Search Path (Options → Files → Support File Search Path) — разовая
настройка **на компьютер**, не на чертёж. Подтверждено живым тестом:
`findfile` нашёл модуль из чертежа, сохранённого в другой папке.
`TRUSTEDPATHS` тоже больше не зависит от папки DWG — путь берётся
через `(findfile "LEP-START.LSP")`, то есть СВОЯ папка модулей.

**DWG теперь может лежать где угодно.** Если у нового пользователя
(например, у коллеги) Support Path ещё не настроен — `LEP-START.LSP`
явно предупредит об этом при загрузке, а не сломается молча.

Подробности и историю правки см. в разделе «Что уже готово и
проверено» ниже.

## ⚠️⚠️⚠️ ВАЖНО: автопривязка `LEP-POLE-ALONE` к трассе — известный риск

`LEP-POLE-ALONE` (отдельная опора без привязки к маршруту) для
ведомости всё равно определяет, к какой трассе она относится — но
делает это ЧИСТО ГЕОМЕТРИЧЕСКИ: находит БЛИЖАЙШУЮ трассу на чертеже
(`LEP:FindNearestRoute` в `LEP-POLE.LSP`) и привязывает опору к ней
по ID.

**"Ближайшая ГЕОМЕТРИЧЕСКИ" не всегда значит "правильная ПО СМЫСЛУ".**
Если отдельная опора стоит близко к границе между территориями двух
разных заявителей (несколько трасс на одном чертеже — обычное дело
в этом проекте), автоматика может молча привязать её не к той трассе,
и это тихо испортит ведомость — без ошибки, без предупреждения о
сбое, просто неверные данные.

**Единственная защита сейчас** — команда печатает в консоль, к какой
трассе привязалась опора ("Опора привязана к трассе LEP_ROUTE_01
(ближайшая, определена автоматически - проверьте, что это верно)."),
и это НУЖНО читать глазами и перепроверять при использовании рядом
с несколькими трассами. Автоматической проверки "а точно ли это та
трасса" пока не существует.

Если это станет реальной проблемой на практике — обсудить более
надёжный механизм (например, спрашивать у пользователя подтверждение,
если найдено больше одной трассы в пределах разумного расстояния, а
не брать просто ближайшую молча).

## ✅ Исправлено (2026-07-10): конфликт `GEOMCONSTRAINT` на угловой опоре

Баг подтверждён пользователем на реальном тесте: угловая опора почти
всегда ставится в точку, где маршрут УЖЕ поворачивает (реальный излом
полилинии). Клик рядом с существующей вершиной заставлял
`LEP:InsertVertexOnRoute` вставлять ВТОРУЮ, почти совпадающую вершину —
на этом участке получался вырожденный (нулевой длины) кусок полилинии,
и `GEOMCONSTRAINT`, пытаясь ещё и привязать туда опору, ловил конфликт
"over-constrain" (диалог "Geometric Constraints" в AutoCAD).

**Исправлено в двух местах:**
- `LEP:InsertVertexOnRoute` (`LEP-POLE.LSP`) — если точка ближе
  `*LEP-Vertex-Snap-Tolerance*` (0,1 м) к уже существующей вершине —
  новая вершина НЕ создаётся, используется существующая.
- Защитный пустой `(command)` (эквивалент Escape в AutoLISP) сразу
  после `GEOMCONSTRAINT` в `LEP-POLE.LSP`/`LEP-END.LSP` — если команда
  всё же не сможет наложить связь по ДРУГОЙ причине, она не будет
  "висеть" и портить остаток цикла расстановки опор (именно это и
  вызывало вторичную ошибку "Select object: _.GEOMCONSTRAINT" на
  следующей опоре).

## ✅ Миграция подписей LEADER → MLEADER (2026-07-15)

Подписи-выноски опор/маршрута/пролёта (`LEP:CreatePoleLabel`,
`LEP:CreateRouteLabel`, `LEP:CreateSpanLabel`) переведены с
классического `LEADER` на `MLEADER`. Причина: у `MLEADER` стрелка +
полка + текст — ОДИН объект (двигаются вместе при редактировании
мышкой), и, в отличие от `LEADER`, можно закрепить в самом стиле
"текст лежит НА полке, подчёркнутый" — вид как в реальных чертежах
коллеги пользователя. У `LEADER` такое поведение получить было
нельзя в принципе (сама история "отступа перед текстом" ниже по
файлу — как раз следствие того, что полка и текст у `LEADER` не так
предсказуемо устроены).

**Как дошли до этого (коротко, полная цепочка тестов — в истории
чата 2026-07-11/2026-07-15):**
1. Живым тестом в консоли подтверждена базовая механика `MLEADER`:
   `(command "_.MLEADER" точка точка "текст")` работает без открытия
   текстового редактора; двухстрочный текст с кириллицей — через код
   разрыва абзаца `\P` прямо внутри строки; полка сама разворачивается
   влево/вправо по направлению точек.
2. `MLEADERSCALE` подтверждён как рабочий общий масштаб-множитель
   (стрелка+полка+текст сразу) — пользователь выбрал коэффициент
   **0.4** на глаз. От этого варианта в итоге ОТКАЗАЛИСЬ в пользу
   пункта 3 — точечная настройка стиля даёт контроль над каждым
   параметром по отдельности, а не один общий множитель.
3. Пользователь вручную поменял 4 настройки стиля "Standard" через
   диалог AutoCAD (Landing distance → 1, Landing Gap → 0, Text color →
   ByLayer, Underline bottom line) и прислал `dictsearch`-дампы стиля
   до/после — по диффу нашли группы DXF, но часть — в комбинации,
   не по отдельности (см. таблицу ниже).
4. Дальше — уже ЧИСТЫЕ ИЗОЛИРОВАННЫЕ живые тесты (по одной группе DXF
   за раз, в новом пустом чертеже, чтобы не путать с предыдущими
   правками — на этом один раз споткнулись: тест в чужом чертеже
   показал "как будто ничего не поменялось", потому что правки стиля
   живут ВНУТРИ конкретного DWG, как и текстовый стиль/блок опоры
   раньше): подтверждена группа 43 (полка), затем случайно поймана
   путаница 44 vs 45 (первая попытка "проверить высоту текста" на
   самом деле поменяла стрелку — 44 и 45 меняли одновременно, тест не
   был чистым), финально изолированным тестом подтверждено: 44 —
   размер стрелки, 45 — высота текста.

**Найденные живым тестом DXF-группы стиля `MLEADERSTYLE`
"Standard"** (полный разбор и что НЕЛЬЗЯ копировать бездумно —
groups 300/340/341/342/343/90 — см. комментарий у констант в
`LEP-CONFIG.LSP`):

| Группа | Смысл | Дефолт AutoCAD | Наше значение | Как подтверждено |
|---|---|---|---|---|
| 43 | Landing distance (длина полки) | 8.0 | 1.0 | изолированный тест |
| 44 | Arrowhead size (размер стрелки) | 4.0 | 0.8 | изолированный тест (значение не финализировано на реальном чертеже) |
| 45 | Text height (высота текста) | 4.0 | = `*LEP-TextHeight*` (1,3) | изолированный тест |
| 42 | Landing gap (зазор полка-текст) | 2.0 | 0.0 | ручная правка пользователя в диалоге |
| 93 | Text color | ACI-подобное | ByLayer (raw -1073741824) | ручная правка пользователя в диалоге |
| 174/178 | Text attachment (лево/право) | 1/1 | 5/5 | ⚠️ КОМБИНАЦИЯ с 295/298, не по отдельности |
| 295/298 | Underline (подчёркивание) | 0/0 | 1/1 | ⚠️ КОМБИНАЦИЯ с 174/178, не по отдельности |
| 342 | Text style handle (наклон/шрифт текста) | хендл "Standard" | хендл `*LEP-TextStyle-Name*` ("LEP-STYLE") | изолированный тест, чистый И боевой чертёж |

**Дизайн-решение: правим НАПРЯМУЮ стиль "Standard"**, а не создаём
отдельный `LEP-`-именной `MLEADERSTYLE` — по аналогии с тем, как
`*LEP-Dim-ArrowSize*` правит глобальную `DIMASZ`, а не отдельный
`DIMSTYLE`. Создание полноценного НОВОГО `MLEADERSTYLE` через
`entmake` "с нуля" не тестировалось живьём (в отличие от `STYLE`/
`LAYER`, для которых уже есть проверенная структура с маркерами
подкласса) — по правилу проекта "не гадать, тестировать" это
отдельная, пока не нужная задача. Побочный эффект (сознательный,
как и с `DIMASZ`): ЛЮБОЙ `MLEADER` в чертеже, включая созданный
пользователем вручную мышкой, получит эти же настройки.

`MLEADERSTYLE` — НЕ классическая именная таблица AutoCAD (в отличие
от `LAYER`/`STYLE`), это объект внутри именованного словаря чертежа
(`namedobjdict` → `ACAD_MLEADERSTYLE` → `"Standard"`). `tblsearch`/
`tblobjname` для него возвращают `nil` — уже ловили живьём
(`entmod` падал с `"bad argument type: lentityp nil"`), правильный
путь — через `dictsearch` (см. `LEP:CreateMLeaderStyle` в
`LEP-SETUP.LSP`).

**Реализация:** `LEP:CreateMLeaderStyle` (`LEP-SETUP.LSP`) выставляет
10 DXF-групп стиля "Standard" через `entget`/`subst`/`entmod`,
вызывается из `C:LEP-SETUP` при каждой загрузке чертежа (как и
`DIMASZ` — не создаёт ничего нового, просто перезаписывает значения,
идемпотентна сама по себе). `LEP:CreatePoleLabel`/`CreateRouteLabel`/
`CreateSpanLabel` теперь вызывают `_.MLEADER` вместо `_.LEADER` —
вызов даже ПРОЩЕ: две точки + текст одной строкой, без повторяющихся
"пусто"-ответов, которые нужны были `LEADER`. Многострочный текст
(статус+тип опоры / класс линии) — через `\P` внутри строки.

**✅ Наклон текста / шрифт (2026-07-15).** Группа 342 (TextStyleHandle)
у стиля "Standard" по умолчанию смотрит на стандартный текстовый
стиль AutoCAD — из-за этого подписи через MLEADER рисовались БЕЗ
наклона 10°/шрифта ISOCPEUR, хотя весь остальной текст на чертеже —
с ними. Подтверждено живым тестом (и на чистом, и на боевом чертеже):
`(tblobjname "STYLE" *LEP-TextStyle-Name*)` → хендл → в группу 342.
Хендл НЕ хранится в CONFIG (специфичен для конкретного чертежа) —
вычисляется заново в `LEP:CreateMLeaderStyle` при каждой загрузке;
важно, что эта функция вызывается СТРОГО ПОСЛЕ `LEP:CreateTextStyle`

В отличие от слоёв (`LEP-SETUP`, безопасно вызывать повторно), блок
символа опоры (`LEP:CreatePoleSymbolBlock`, `LEP-POLESYM.LSP`)
создаётся **только если его ещё нет** в чертеже — при каждой новой
загрузке `LEP-START.LSP` геометрия НЕ обновляется автоматически.
Причина: честный "передефайн" существующего блока через `-BLOCK`
(с подтверждением перезаписи) не протестирован вживую в консоли
AutoCAD — решили не рисковать (тот же принцип, по которому уже не раз
ловили баги на неправильном порядке аргументов `command`). Если после
визуальной проверки геометрию трапеции понадобится поправить — на
чертеже без вставленных опор проще всего удалить блок вручную
(`PURGE`) и заново загрузить `LEP-START.LSP`; если опоры уже
расставлены — нужно протестировать передефайн вживую и добавить в код.

## Общий порядок работы

1. Открываем новый чертёж AutoCAD (где угодно — привязка к папке с
   модулями снята 2026-07-16, см. раздел выше).
2. Вставляем подложку — скриншот кадастровой карты (`IMAGEATTACH`).
3. **Ничего загружать руками не нужно** — `LEP-START.LSP` подхватывается
   автоматически при открытии любого чертежа через `acaddoc.lsp`
   (штатный автозагрузчик AutoCAD, есть и на Mac, и на Windows).
   Ручной `APPLOAD` → `LEP-START.LSP` по-прежнему работает и удобен для
   ПЕРЕЗАГРУЗКИ кода после правок, без переоткрытия чертежа.
   `LEP-SETUP` (создание всех слоёв проекта) вызывается автоматически
   внутри `LEP-START.LSP` при каждой загрузке, отдельно её запускать не
   нужно (раньше это был отдельный пункт списка — убрали, чтобы не
   забывали). `LEP:CreateLayer`
   безопасно вызывать повторно: если слой уже есть, он просто
   пропускается, ничего не пересоздаётся. После автозапуска текущим
   слоем становится специальный `LEP-MANUAL` (см. "Что уже готово") —
   не технический слой, чтобы случайная ручная линия не попала в
   ВЛ/КЛ/опоры и не испортила ведомость.
4. `LEP-SCALE` — калибровка масштаба подложки по двум точкам с
   известным реальным расстоянием (1 ед. AutoCAD = 1 м после этого).
   После калибровки подложка принудительно перекладывается на слой
   `LEP-KADASTR` (могла оказаться на другом — `-LAYER Make` в
   `LEP-SETUP` всегда делает только что созданный слой текущим, см.
   пункт 3 выше) и уходит в конец порядка отрисовки (`DRAWORDER`),
   чтобы маршрут/опоры поверх нее не "проваливались" под неё зрительно.
5. `LEP-ROUTE` — черчение маршрута (полилиния), Enter — конец
   построения. Сразу после этого программа спрашивает **класс
   напряжения маршрута** (10 кВ / 0,4 кВ, `*LEP-VoltageClasses*` в
   CONFIG) — ОДИН РАЗ на весь маршрут (в жизни напряжение не меняется
   посреди трассы: между 10кВ и 0,4кВ участками всегда стоит МТП, а
   значит с точки зрения программы это уже новый маршрут). Класс
   хранится в XDATA маршрута (`VCLASS`) и дальше определяет список
   марок провода в `LEP-SPAN` и вторую строку подписи опоры в
   `LEP-POLE`. Каждый маршрут получает свой уникальный ID
   (`LEP_ROUTE_01`, `LEP_ROUTE_02`...) для разделения линий к разным
   заявителям в будущей ведомости — на одном чертеже бывает несколько
   трасс. Сразу после построения у начальной точки маршрута
   появляется подпись "Маршрут NN", чтобы было видно на самом
   чертеже, какой маршрут где, а не только внутри XDATA. Сама
   полилиния маршрута рисуется на служебном слое `LEP-ROUTE-SERVICE`
   (НЕ на слое ВЛ) — это не настоящая линия, а "арматура" для
   констрейнтов опор, печать у неё всегда выключена. Видимость на
   экране — команда `LEP-ROUTEVIS` (включить перед кликом по маршруту
   в `LEP-POLE`/`LEP-SPAN`, выключить, чтобы не перекрывала пунктир КЛ
   при осмотре). **✅ 2026-07-15 (просьба пользователя)**: подпись
   "Маршрут NN" тоже переехала на этот служебный слой (была на
   `LEP-TEXT`, как и остальные подписи проекта) — она чисто
   техническая, не должна печататься/попадать в PDF, а слой
   `LEP-ROUTE-SERVICE` уже настроен так изначально. Побочный эффект
   (ожидаемый, обсуждён): теперь подпись прячется/появляется вместе с
   линией маршрута через `LEP-ROUTEVIS`, а не видна всегда, как
   раньше. Проверено, что это ничего не ломает — все места, которые
   сканируют этот слой (`LEP:GetMaxRouteNumber`, `LEP:FindNearestRoute`,
   ведомость), фильтруют строго по типу `LWPOLYLINE`, а подпись —
   `MULTILEADER`, под фильтр не попадает.
6. `LEP-POLE` — РУЧНАЯ расстановка опор в цикле:
   - клик рядом с трассой → точка проецируется на линию → вставляется
     новая вершина полилинии → опора садится туда;
   - **✅ 2026-07-15 (просьба пользователя)**: начиная со ВТОРОЙ опоры
     можно ВВЕСТИ расстояние от предыдущей ЧИСЛОМ СО ЗНАКОМ
     (`LEP:PromptNextPolePoint`) вместо клика "на глаз" — точка
     ставится вдоль трассы через `LEP:GetPointAtDistance`
     (`LEP-POLYLINE.LSP`). Знак = направление: "+" от подписи
     "Маршрут NN" (стоит у ПЕРВОЙ вершины маршрута) к дальнему концу,
     "-" обратно к подписи — готовый бесплатный ориентир направления
     на чертеже, без дополнительной графики. **⚠️ ФИКС того же дня**:
     первая версия угадывала направление ПО ПОЗИЦИИ первой опоры (к
     какой вершине маршрута ближе) — ломалось, если первая опора стояла
     у СЕРЕДИНЫ трассы (сравнение сводилось к случайным долям
     миллиметра). Знак убирает угадайку целиком, работает из любой
     точки трассы. Если расстояние превышает оставшуюся длину трассы —
     продолжает прямо (та же экстраполяция, что у МТП/ЩУ за концом
     трассы в `LEP-END`). Enter вместо числа — как раньше, клик мышкой,
     но теперь с базовой точкой (резинка от самого AutoCAD). **✅ ФИКС
     2026-07-15**: подсказка расстояния/угла у курсора (Dynamic
     Input), на которую рассчитывали изначально — проверено
     пользователем вживую: НЕ появляется у голого `getpoint` из LISP
     (резинка есть, числа нет) — похоже, это фишка только штатных
     команд AutoCAD (`LINE` и т.п.), не настройка, которую можно
     включить. Вместо неё — эхо ФАКТИЧЕСКОГО расстояния СРАЗУ ПОСЛЕ
     клика (не во время протаскивания, но хотя бы сразу видно
     результат, без ручного замера). Готовой "стрелочной" линии для
     визуализации направления в AutoCAD нет (проверено) — самодельная
     была бы той же мороки, что и убранная `LEP_CABLE`, не стали
     делать;
   - выбор типа опоры — номером в консоли по умолчанию (можно
     переключить на диалог со списком мышкой через `*LEP-UseDCL*` в
     CONFIG, но консоль быстрее — так и оставили);
   - выбор статуса (Проект/Сущ., по умолчанию Проект) — общая функция
     `LEP:GetStatus` (в `LEP-UTILS.LSP`), используется и в `LEP-SPAN`;
   - **символ опоры** (с 2026-07-10, `LEP-POLESYM.LSP`) — трапеция
     (1×1м, узкая сторона 0,7м) + крест через центр (1,07м по каждой
     оси, ФИКСИРОВАННО серый, `*LEP-Color-PoleCross*` — не зависит от
     цвета/статуса самой опоры) вместо старой заглушки `test-block`.
     Цвет опоры (Проект.) — оранжевый (`*LEP-Color-Proj-VL*`, был
     красный — совпадал со служебной линией маршрута). Широкая сторона
     всегда смотрит к НАЧАЛУ маршрута, узкая — к концу (поворот
     считается по направлению отрезка трассы под опорой). Толщина
     линии — по статусу (Проект. жирнее Сущ., см. `*LEP-LWeight-Proj*`/
     `*LEP-LWeight-Exist*`). По типу опоры (`*LEP-PoleStands*`)
     автоматически рисуется 1/2/3 трапеции (главная опора + откос(ы)
     для анкерных/угловых типов, расстояние между ними
     `*LEP-Pole-Sym-Offset*` = 2м) — см. **⚠️ предупреждение вверху
     README** про черновой угол разворота откоса;
   - ГЛАВНАЯ трапеция привязывается к вершине маршрута
     (`GEOMCONSTRAINT`) — откосы (если есть) НЕ привязаны, чисто
     визуальная деталь;
   - подпись-выноска, теперь ДВУХСТРОЧНАЯ: "[статус]. оп. [тип]" +
     класс линии маршрута ("ВЛЗ-10 кВ"/"ВЛИ-0,4 кВ",
     `*LEP-VoltageClassLabel*`) — раньше был только один вопрос без
     ответа (класс появлялся лишь после `LEP-SPAN`), теперь известен
     сразу, т.к. выбирается один раз при `LEP-ROUTE`;
   - Enter без точки - выход из цикла.
   - **`LEP-POLE-ALONE`** — та же опора (тип/статус/подпись), но БЕЗ
     привязки к трассе: ставится ровно в клик, без проекции/вершины/
     `GEOMCONSTRAINT`/поворота (символ ставится без разворота — нет
     маршрута, от которого его считать), свободно двигается потом. См.
     **⚠️ ПОДВОДНЫЙ КАМЕНЬ** ниже про привязку к трассе для ведомости.
   - **✅ `LEP-POLE-DELETE` / `LEP-POLE-MOVE` (2026-07-15, по просьбе
     пользователя)**: опора — это НЕСКОЛЬКО независимых объектов
     (блок + подпись-выноска отдельным `MLEADER` + откосы у анкерных/
     угловых типов) без единой связи между ними в AutoCAD. Простое
     стирание блока мышкой оставляло подпись висеть в воздухе (**живой
     тест 2026-07-15 подтвердил**: `entdel` блока опоры НЕ трогает её
     подпись) и откосы — сиротами. `LEP:DeletePoleGroup` убирает все
     три вида объектов разом: подпись — по хендлу, сохранённому в
     XDATA опоры при вставке (ключ `LABELHANDLE`, `LEP:AddPoleData`);
     откосы — по признаку "блок `LEP-POLE-SYM` рядом, но БЕЗ XDATA"
     (у откосов её нет вообще, надёжнее, чем просто близость).
     Вершина трассы, где стояла опора, НЕ убирается — служебный слой,
     не печатается, не попадает в ведомость, безвредный технический
     хвостик; гоняться за ним рискованнее (можно задеть чужую
     вершину), чем оставить.
     `LEP-POLE-DELETE` — клик по опоре, убирает всё разом.
     `LEP-POLE-MOVE` — читает тип/статус старой опоры из XDATA,
     удаляет её и ставит новую (`LEP:PlacePoleOnRoute` — общая функция
     вставки, вынесена из `LEP-POLE` 2026-07-15) на новой точке — не
     нужно вручную тащить блок мышкой, рискуя, что пролёт (`LEP-SPAN`)
     останется привязан к СТАРОЙ геометрии, если `GEOMCONSTRAINT`
     почему-то не удержал связь опоры с трассой.
7. **`LEP-END`** (новое, 2026-07-10) — оконечное оборудование
   маршрута, у самого конца трассы:
   - выбор типа: **ПУ** (0,4 кВ, мелкий заявитель) — 1 опора
     `*LEP-End-PoleType-PU*` (**"П23"**, ⚠️ с 2026-08-03 у ПУ свой тип,
     см. раздел «✅ У окончания ПУ свой тип опоры» ниже) с подписью
     "ПУ"; либо **МТП**
     (10 кВ, крупный заявитель) — 3 такие же опоры подряд (шаг
     `*LEP-End-MTP-Spacing1*`/`-Spacing2*`, 3м/2м), подписи РЛК / МТП-
     160 кВА / ЩУ на 1-й/2-й/3-й соответственно — три подписи
     РАЗВЕДЕНЫ в разные стороны (`*LEP-End-LabelAngle-RLK*`/`-MTP*`/
     `-SchU*` в CONFIG, влево-вверх/прямо-вверх/вправо-вверх), т.к.
     опоры стоят близко друг к другу и подписи в одну сторону
     накладывались (замечено на реальном тесте, 2026-07-10);
   - первая опора ставится как в `LEP-POLE` (проекция на маршрут,
     новая вершина, `GEOMCONSTRAINT`) — прямое продолжение трассы;
     2-я и 3-я опоры блока МТП — дальше по тому же направлению, БЕЗ
     проекции (это уже за пределами нарисованной полилинии). **✅ ФИКС
     2026-07-15**: направление теперь определяется автоматически — если
     точка установки ближе к ПЕРВОЙ вершине маршрута, чем к ПОСЛЕДНЕЙ
     (сравнение через `LEP:GetVertices`), направление разворачивается
     на 180°, чтобы опоры 2/3 всегда уезжали НАРУЖУ от трассы, а не
     налезали на неё — раньше блок МТП корректно работал только с
     одного конца маршрута (последней вершины), с первой опоры 2/3
     заезжали в тело уже нарисованной линии;
   - тип опоры зафиксирован, не спрашивается — по прямому указанию
     пользователя. ⚠️ С 2026-08-03 он **не один на всех**: у ПУ «П23»
     (`*LEP-End-PoleType-PU*`), у СТП и у всех трёх опор МТП прежний
     «П20-3Н» (`*LEP-End-PoleType*`). **✅ ФИКС 2026-07-15**: статус (Проект./
     Сущ.) раньше был зашит намертво в "Проект." — оказалось,
     существующее оконечное оборудование тоже бывает (например при
     подключении к уже стоящей подстанции); теперь спрашивается один
     раз на весь блок (`LEP:GetStatus`, та же функция, что у обычных
     опор), честно попадает в XDATA через `LEP:AddEquipData`;
   - РЛК/МТП/ЩУ/ПУ — НЕ отдельная графика, только текстовые подписи
     рядом с опорой (подтверждено реальными чертежами пользователя);
   - команда ставит ОДНУ концовку и завершается (без цикла — на
     маршрут обычно ровно одна концовка; нужна ещё — запустить
     `LEP-END` снова). Enter вместо выбора типа — отмена.
   - **✅ ТРЕТИЙ ПУНКТ 2026-07-15 — "ПУ на существующую опору"** (по
     просьбе пользователя: не заводить отдельную команду ради этого,
     "команд и так хватает"; и не плодить новую опору, если реальное
     подключение идёт к уже стоящей). Выбор типа теперь ПЕРВЫМ вопросом
     (не после выбора маршрута — этому пункту маршрут не нужен вообще).
     Клик по существующей опоре → строка **"+ проект. ПУ"** дописывается
     прямо в ЕЁ ЖЕ подпись (`LEP:AppendMLeaderText`, `LEP-UTILS.LSP`) —
     подтверждено живым тестом 2026-07-15: текст выноски лежит в группе
     DXF 304, которая у `MULTILEADER` встречается ещё раз глубже как
     служебный маркер "LEADER_LINE{" (та же природа ловушки, что и с
     группой 292 у фона подписи) — коллизии нет, `assoc` берёт ПЕРВОЕ
     вхождение, это и есть настоящий текст. Никакой новой геометрии —
     ни трапеции, ни вершины, ни `GEOMCONSTRAINT`. Данные для ведомости —
     `LEP:AddEquipToExistingPole` (`LEP-DATA.LSP`), НЕ обычная
     `LEP:AddEquipData` (та ПЕРЕЗАПИСАЛА бы XDATA опоры целиком, стерев
     её `LABELHANDLE` и подменив её собственный статус Сущ. на статус
     оборудования) — читает все текущие поля опоры и переписывает их же
     обратно, добавляя `EQUIP`/`EQUIPSTATUS` (статус ИМЕННО оборудования,
     отдельно от статуса самой опоры — опора остаётся Сущ., новое
     оборудование на ней — Проект., это не противоречие). См. также
     `LEP-REPORT.LSP`, ЭТАП 2.5 — без отдельного скана слоя существующих
     опор такое оборудование молча не попало бы в CSV (обычный скан
     смотрит только слой проектируемых опор).
8. `LEP-SPAN` — классификация пролётов, тоже в цикле:
   - клик ПО БЛОКУ первой опоры пролёта, затем ПО БЛОКУ второй;
   - выбор типа прокладки (ВЛ/КЛ), марки провода/кабеля и статуса
     (Проект/Сущ., та же `LEP:GetStatus`, что и у опор). Список марок
     провода ВЛ зависит от класса напряжения маршрута (`VCLASS`) —
     `*LEP-WireTypes-VL-10*` (СИП-3) для 10 кВ, `*LEP-WireTypes-VL-04*`
     (СИП-2) для 0,4 кВ — это разные провода физически, СИП-2 только
     для низкого напряжения (0,6-1кВ), СИП-3 только для магистрали;
   - создаётся отдельный объект-полилиния под этот пролёт, на своём
     слое/типе линии;
   - **расстояние между опорами (по прямой) и реальная длина провода/
     кабеля — теперь РАЗНЫЕ числа**: подпись пролёта и XDATA `LENGTH`
     (а значит и ведомость) показывают длину МАТЕРИАЛА с запасом —
     ВЛ +`*LEP-Sag-VL*`% (по умолчанию 2%, провис), КЛ +`*LEP-KL-Reserve*`
     м (по умолчанию 6 м, подъём на опору с двух сторон) — округлено
     ВВЕРХ до целого метра. Отдельно — размерная линия (`DIMALIGNED`,
     параллельно самому пролёту, а не всегда горизонтально/вертикально
     как у `DIMLINEAR` — пролёт может идти под любым углом; слой
     `LEP-DIM`) с ПРЯМЫМ расстоянием между опорами, округлённым по
     обычным правилам математики (не для закупки, а для наглядности);
   - ВЛ — сплошная линия слоя `LEP-PROJ-VL` (оранжевый); КЛ — **✅
     2026-07-15: тоже сплошная линия** (слоя `LEP-PROJ-KL`, синий) —
     раньше был свой тип линии `LEP_CABLE` со штампом "K" в разрывах,

## GPS-точки из GeoJSON → зелёные кружки-ориентиры (2026-07-20)

Новый модуль `LEP-GEOPOINTS.LSP`. Задача пользователя: в поле снимают
GPS-координаты будущих опор (экспорт в GeoJSON, WGS84), нужно
поставить на чертёж временные зелёные кружки в тех же точках, что и
подоснова (МСК-47) — дальше пользователь рядом расставляет настоящие
символы опор вручную. Кружки не часть готового чертежа, только рабочий
ориентир — отдельный непечатаемый слой `LEP-GEOPOINTS` и отдельная
команда полной очистки.

**Первая идея (ОТВЕРГНУТА): своя формула перевода WGS84 → МСК-47.**
Другая ИИ-модель подобрала квадратичную полиномиальную регрессию
(6 коэффициентов на X, 6 на Y) по 25 калибровочным парам координат
одного участка трассы (пользователь перевёл их через онлайн-калькулятор
и прислал оба набора). Проверка (см. историю чата 2026-07-20): формула
легла на калибровочные точки почти идеально — расхождение 0.0005–0.011 м
(меньше сантиметра). Выглядело отлично, НО пользователь сам
проверил формулу на ТРЁХ РАЗНЫХ зонах и обнаружил, что у каждой зоны —
своё смещение. Это ожидаемо: у каждой из трёх зон МСК-47 (условно
"полосы" по 3° долготы) свой осевой меридиан и своё смещение по X
(зона 1 → 1 250 000, зона 2 → 2 250 000, зона 3 → 3 250 000), а сама
проекция внутри зоны нелинейна — локальная подгонка одного узкого
участка (все 25 калибровочных точек лежали в одном коридоре ~500 м)
не может "знать" об этой глобальной структуре и не переживает переезд
на другой участок. Формула отвергнута целиком, коэффициенты нигде в
проекте не сохранены.

**Итоговое решение: перевод координат делает пользователь САМ, через
проверенный сайт-конвертер.** Пользователь прислал скриншот конвертера
с явно указанным официальным кодом `EPSG:6334702` (МСК-47, зона 2,
Ленинградская область) — это НЕ самодельное приближение, а
зарегистрированная в реестре EPSG система координат (полноценная
геодезическая трансформация датума + проекция Гаусса-Крюгера + все
нужные поправки уже "внутри" этого кода). LISP координаты НЕ считает
вообще — только читает готовый результат. Формат подтверждён по
скриншоту: разделитель дробной части — точка, между координатами —
запятая, вход "N,E" (широта,долгота), выход тоже "N,E" (северная,
восточная), одна пара на строку, тот же порядок строк, что и на входе.

**Три команды, три шага (не одна команда "GeoJSON → чертёж сразу"):**

1. `LEP-GEOPOINTS-EXTRACT` — **ЕДИНСТВЕННЫЙ** ручной выбор файла во всей
   цепочке (`getfiled` на geojson, чтобы не вводить путь руками) →
   собственный узкий разбор структуры (`LEP:GeoJSON-Parse`, через
   `vl-string-search`/`substr` — в AutoLISP нет ни `regex`, ни готовой
   JSON-библиотеки, поэтому это НЕ полноценный JSON-парсер, а разбор
   под конкретную структуру экспорта: `"coordinates": [lon, lat]` +
   `"properties": {"name": "..."}`) → три файла **рядом с ЧЕРТЕЖОМ**
   (`DWGPREFIX`, ✅ ФИКС 2026-07-20 по прямой просьбе пользователя —
   первая версия писала файлы рядом с САМИМ GEOJSON, что могло быть
   произвольной папкой типа `~/Downloads`; теперь то же место, что и у
   CSV-ведомости в `LEP-REPORT.LSP`):
   - `geopoints-coords.txt` — только "широта,долгота" по строке, БЕЗ
     названий — специально, чтобы можно было выделить весь файл и
     вставить в конвертер одним действием, не вычищая лишнее руками;
   - `geopoints-names.txt` — только названия точек, в ТОМ ЖЕ порядке
     строк (хранится "за кулисами", пока координаты гуляют туда-сюда
     через внешний конвертер — единственный способ не потерять
     подписи типа "Анкерная опора с откосом в сторону тп", которые
     нельзя вставить в конвертер вместе с числами);
   - `geopoints-converted.txt` — создаётся ПУСТЫМ (✅ ФИКС 2026-07-20,
     по просьбе пользователя), но ТОЛЬКО если его ещё нет: при
     повторном запуске `EXTRACT` (например, добавили новые точки в
     geojson) уже вставленный пользователем результат конвертера не
     затирается молча.
2. (ручной шаг пользователя) — открыть `geopoints-coords.txt`,
   скопировать всё, вставить в конвертер WGS84 → МСК-47 зона 2,
   результат вставить в уже готовый `geopoints-converted.txt` и
   сохранить.
3. `LEP-GEOPOINTS-DRAW` — ✅ ФИКС 2026-07-20: БЕЗ диалога выбора файла
   вообще (по просьбе пользователя — "выбирать руками надо только
   json"), сама читает `geopoints-converted.txt` и
   `geopoints-names.txt` из папки чертежа (`DWGPREFIX`, те же
   фиксированные имена, что создаёт `EXTRACT`). **Сверяет количество
   строк** координат и названий — при расхождении НИЧЕГО не рисует
   вообще (не "рисуем сколько смогли") и печатает громкую ошибку: при
   рассинхроне невозможно понять, какая строка какой точке
   соответствует, тихая частичная отрисовка привела бы к подписям на
   чужих точках без единого сообщения об ошибке. Рисует зелёный круг
   (`*LEP-GeoPoints-Diameter*`, 1 м) + подпись рядом для каждой пары.
4. `LEP-GEOPOINTS-CLEAR` — стирает все объекты со слоя одной командой
   (слой остаётся, не пересоздаётся, готов для следующей партии).

**⚠️ Перестановка X/Y — самое опасное место во всей схеме.** Сайт
конвертера отдаёт результат как "N,E" (северная, восточная) — это НЕ
то же самое, что чертёжные X/Y. У подосновы этого проекта (разобран
реальный текстовый объект на чертеже, свойства AutoCAD Properties,
2026-07-20): чертёжный X ≈ 2 247 089 (это "восточная" — совпадает по
порядку величины со смещением зоны 2 МСК-47, 2 250 000), чертёжный
Y ≈ 454 672 (это "северная"). Значит при вставке в чертёж нужно
СВОПНУТЬ: `DrawPt = (list Easting Northing 0.0)`, а не `(list Northing
Easting 0.0)` "как пришло". `LEP-GEOPOINTS-DRAW` делает эту
перестановку явно, с комментарием прямо в коде — если код когда-нибудь
будут менять, ⚠️ НЕ убирать перестановку и не менять порядок аргументов
не глядя.

**✅ Разбор GeoJSON подтверждён живым тестом (2026-07-20).** Первая
попытка живого теста (отдельный тестовый файл, до появления самого
модуля) сорвалась НЕ из-за ошибки в логике: при попытке вставить

**Рекомендация перед доверием первой партии точек**: после

## Правки по итогам просмотра готовой программы (2026-07-22)

Пользователь прислал построчный список заметок после просмотра работы
программы. Реализовано в этой сессии:

1. **Длина ВЛ на чертеже - без запаса.** Подпись пролёта ВЛ теперь
   показывает СЫРОЕ расстояние (без `*LEP-Sag-VL*`% на провис) -
   запас остаётся ТОЛЬКО в ведомости (XDATA `LENGTH`, как и раньше).
   **КЛ - НЕ так** (уточнение пользователя, "до дальнейших указаний"):
   запас на подъём кабеля (`*LEP-KL-Reserve*`, +3м с каждой стороны) -
   это РЕАЛЬНАЯ физическая длина кабеля, а не просто "запас на
   закупку", как провис ВЛ - подпись КЛ по-прежнему показывает длину
   С запасом, как и раньше.
2. **Подпись объединяется на весь однородный участок трассы**, а не
   ставится у каждого пролёта отдельно - "тип прокладки не меняется"
   означает совпадение марки провода/кабеля И статуса (Проект/Сущ).
   Механизм (полностью новый, `LEP-SPAN.LSP`):
   - У каждого пролёта в XDATA теперь хранятся хендлы ОБЕИХ опор,
     которые он соединяет (`POLE1HANDLE`/`POLE2HANDLE`) - это НАДЁЖНЫЙ
     способ найти "соседний пролёт" (по хендлу опоры, не по совпадению
     координат с допуском - на допуске уже ловили баги в этом проекте,
     см. `*LEP-Vertex-Snap-Tolerance*`). Работает независимо от того,
     в каком порядке пользователь кликает пролёты вдоль трассы.
   - После создания КАЖДОГО нового пролёта - автопроверка соседей с
     обеих сторон (`LEP:GetSpanNeighbors`), совпадающих по марке и
     статусу. Если сосед уже был частью большей объединённой группы -
     подхватывается ВСЯ группа целиком (`LEP:FindGroupMembers`, по
     общему `LABELHANDLE`), а не только один сосед - поэтому вставка
     пролёта "мостиком" между двумя уже готовыми однородными участками
     автоматически сливает их в один.
   - Старая(-ые) подпись(-и) участников удаляются, создаётся ОДНА
     новая на середину КРАЙНИХ точек всей группы (по индексу вершины
     вдоль маршрута, не по порядку создания пролётов), новый
     `LABELHANDLE` прописывается ВСЕМ пролётам группы.
   - Итоговая длина группы: для ВЛ - сумма СЫРЫХ длин участников
     (округление один раз, в конце); для КЛ - сумма уже готовых
     `LENGTH` (с запасом) участников.
   - Размерная линия (`DIMALIGNED`) НЕ объединяется - остаётся у
     каждого пролёта отдельно, как и раньше.
   - **⚠️ Ограничение**: пролёты, нарисованные ДО этого обновления, не
     имеют `POLE1HANDLE`/`POLE2HANDLE` - они просто не найдутся
     соседями ни для кого (не ошибка, а осознанный предел).
3. **"+ подъём кабеля по опоре"** - если пролёт КЛ, эта фраза
   автоматически дописывается в подписи ОБЕИХ опор (через
   `LEP:AppendMLeaderText`, тот же приём, что и "+ проект. ПУ" в
   `LEP-END.LSP`). Защита от двойного дописывания у опоры на стыке
   двух КЛ-пролётов подряд - проверка текста подписи перед добавлением.
4. **Способ прокладки КЛ (ГНБ/Траншея)** - новый вопрос в `LEP-SPAN`,
   ТОЛЬКО для Проект. КЛ (Сущ. КЛ уже проложена каким-то способом
   де-факто, спрашивать не о чем). Каждый способ - свой слой
   (`LEP-PROJ-KL-GNB`/`LEP-PROJ-KL-TRENCH`) со своим цветом.
5. **Цвета по классу напряжения x статус** - у ВЛ и опор раньше было 2
   слоя (Проект./Сущ.) на оба класса напряжения сразу; теперь 4 (класс
   x статус): 10кВ Проект - оранжевый (без изменений), 0,4кВ Проект -

### Дополнение 2026-07-24: МТП на 6 кВ

Пользователь: «добавь плиз в LEP-END МТП 6 кВ, всё аналогично 10 кВ».

**Сделано ровно два содержательных изменения** — и это тот редкий
приятный случай, когда «аналогично» действительно означает «почти
ничего не трогаем»:

1. Две новые строки в `*LEP-MTP-Types*` (`LEP-CONFIG.LSP`):
   `"МТП-160/6/0,4"` и `"МТП-250/6/0,4"`. Мощности те же, что у 10 кВ —
   меняется только средняя часть строки «мощность/**ВН**/НН».
2. Текст пункта меню в `C:LEP-END`: «МТП (10 кВ …)» → «МТП (10/6 кВ …)».

**Почему больше ничего не понадобилось:**

- геометрия блока МТП (3 опоры, шаг 3 м/2 м, направление наружу от
  трассы), подписи РЛК/ЩУ, углы разведения подписей, тип опоры, статус,
  слой опор — **от класса напряжения не зависят вообще**;
- в ведомости 6-киловольтные МТП становятся отдельными строками
  **автоматически**, благодаря механизму от 2026-07-16: выбранная
  строка целиком пишется в XDATA `EQUIP`, ведомость её не
  «вычисляет заново» из конфига (см. `LEP:GetEquipLabel`,
  `LEP-REPORT.LSP`). Именно ради таких случаев это и делалось;
- `LEP:CreateKtpLabel` (КТП) подставляет класс маршрута в строку
  подписи сам — для 6 кВ работает без правок, проверено чтением кода.

**⚠️ Список НЕ фильтруется по классу маршрута — сознательно.**
Программа знает `VCLASS` маршрута (читается в `C:LEP-END` за 12 строк до
вопроса о мощности) и могла бы показывать только два подходящих пункта.
Пользователь выбрал видеть **все четыре** — на случай, если понадобится
поставить МТП не того класса, что у трассы. Ответственность за выбор
строки — на пользователе.

**⚠️ Но фолбэк на Enter пришлось починить — это была бы мина.**
Если пользователь нажимал Enter вместо выбора мощности, подставлялась
константа `*LEP-Label-MTP*` = `"МТП-160/10/0,4"`. Пока МТП были только
десятикиловольтные, это было безобидно; с появлением 6 кВ случайный
Enter на 6-киловольтном маршруте **молча поставил бы МТП на 10 кВ**, и
она ушла бы в ведомость отдельной НЕВЕРНОЙ строкой (название пишется в
XDATA целиком — как раз тот механизм, который в остальном нам помогает).

Новая `LEP:GetDefaultMtpLabel` (`LEP-END.LSP`) берёт первую строку из
`*LEP-MTP-Types*`, у которой высокая сторона совпадает с классом
маршрута — ищет подстроку `"/6/"` **со слэшами с обеих сторон** (без них
`6` случайно нашлось бы внутри другого числа). Не нашла (класс 0,4 кВ,
или старый маршрут вообще без `VCLASS`) — откат на прежнюю константу,
поведение как раньше. Решение переживёт добавление новых мощностей и
новых классов без правки функции.

Это **не фильтрация списка** — правится только то, что подставляется,
когда пользователь не выбрал ничего.

## ✅ Параллельный сдвиг нескольких проводов на одной паре опор (2026-07-22)

Пользователь описал реальный сценарий: маршрут 2 идёт через ТЕ ЖЕ
существующие опоры, что и маршрут 1 (например МТП-1-2-3-4), а дальше
расходится в другую сторону - и подчеркнул, что маршрут 2 нужно "как-то
показать рядом" с маршрутом 1, отдельно подписать. Без специальной
обработки оба пролёта (маршрут 1 и маршрут 2 на общем участке МТП-1-2-
3-4) легли бы ГЕОМЕТРИЧЕСКИ ТОЧНО друг на друга (одни и те же
координаты вершин) - визуально одна линия, подписи друг на друге,
нечитаемо, хотя данные (ведомость, XDATA) честно разделены по разным
`ROUTE`. Та же проблема одинаково касается и "два провода на ОДНОМ
маршруте" (одна и та же пара опор, просто разные марки/статус) - более
ранний ответ "это уже работает" был неполным: верно для ведомости,
неверно для самого чертежа.

**Решение**: перед созданием пролёта - `LEP:FindSamePolePairSpans`
(`LEP-SPAN.LSP`) находит ВСЕ уже существующие пролёты между ТОЙ ЖЕ
парой опор (по хендлам `POLE1HANDLE`/`POLE2HANDLE`, в любом порядке,
независимо от того, какому маршруту они принадлежат). Если такие уже
есть - новая линия сдвигается ПЕРПЕНДИКУЛЯРНО трассе на
`*LEP-Span-ParallelOffset*` (0,5 м, `LEP-CONFIG.LSP`) x номер по
счёту, ПООЧЕРЁДНО в разные стороны от центра (`LEP:GetParallelOffset`) -
1-й пролёт на паре опор остаётся на месте без сдвига, 2-й уходит на
+0,5м, 3-й на -0,5м, 4-й на +1,0м и т.д. Сдвигается ВЕСЬ путь
(`SubVerts`, включая промежуточные изгибы, если есть) как единое целое
через `LEP:OffsetPointList` - перпендикуляр к направлению P1→P2, тот же
приём, что уже используется в `LEP:CreateSpanDimension` для сдвига
размерной линии.

Подпись пролёта автоматически "переезжает" вместе со сдвинутой
геометрией (её точка отсчёта - середина СМЕЩЁННЫХ вершин, отдельно
ничего не трогали) - несколько параллельных проводов на общем участке
теперь читаются раздельно.

**✅ Размерная линия** (`LEP:CreateSpanDimension`, прямое расстояние
опора-опора) рисуется ТОЛЬКО у первого пролёта на паре опор
(`ParallelN = 0`) - у остальных геометрия (расстояние между теми же
двумя опорами) идентична, повторять её незачем, только мусор на
чертеже.

## ✅ Геометрическое определение маршрута пролёта (2026-07-22)

Проблема, которую сформулировал пользователь: "Я проложил маршрут 1,
расставил опоры, задал пролёты. Далее появляется маршрут 2, я его
прокладываю ПОВЕРХ существующих опор. Как теперь задать пролёты? Я
выберу две существующие опоры - как программа поймёт, что этот пролёт
относится к маршруту 2?"

**Ответ - никак не понимала.** `LEP-SPAN` брал номер маршрута НЕ из
геометрии, а буквально копировал `ROUTE` из XDATA кликнутой опоры. А
там записан тот маршрут, которым опору СОЗДАЛИ (маршрут 1), навсегда -
про маршрут 2, проложенный позже поверх неё, опора не знает ничего.
Программа физически не могла догадаться: она не спрашивала, она брала
готовое значение.

**Решение - определять маршрут ГЕОМЕТРИЧЕСКИ.** Информация-то есть: 
полилиния маршрута 2 реально нарисована и реально проходит через эти
точки. `LEP:FindRoutesThroughPoints` (`LEP-SPAN.LSP`) сканирует все
трассы чертежа и находит те, что проходят в пределах
`*LEP-Route-Detect-Tolerance*` (1 м, `LEP-CONFIG.LSP`) от ОБЕИХ
кликнутых опор. Расстояние считается через уже готовую
`LEP:FindNearestSegment` (`LEP-POLE.LSP`) - новой геометрии не
понадобилось. Дальше:

- **1 кандидат** (обычный случай - через опоры проходит только их
  родная трасса) → берётся молча, ни одного нового вопроса, поведение
  ничем не отличается от прежнего;
- **несколько кандидатов** (собственно случай пользователя - общий
  участок двух фидеров) → ОДИН вопрос со списком ID этих трасс, и
  **ответ запоминается до конца сессии команды** (`SessionRouteEnt`) -
  следующие пролёты на неоднозначных парах опор идут туда же без
  переспроса;
- **ноль кандидатов** (трассу стёрли и т.п.) → откат на `ROUTE` опоры,
  ровно старое поведение.

Геометрия пролёта нарезается из вершин ВЫБРАННОГО маршрута, класс
напряжения (а значит и список марок провода) тоже берётся у него -
если маршрут 2 после общего участка уходит в сторону, его пролёты
лягут по его собственной полилинии корректно. `RouteID` в XDATA
пролёта - тоже выбранный маршрут, поэтому ведомость, объединение
подписей и `LEP-SPAN-REPAIR` продолжают работать сами, без единой
правки. Параллельный сдвиг (см. раздел выше) тоже не тронут - он
завязан на хендлы ОПОР, а не на номер маршрута, поэтому два фидера на
общем участке автоматически разъедутся по 0,5 м и будут читаемы.

**⚠️ Два осознанных решения, зафиксировать:**

1. **Опоры общего участка ОСТАЮТСЯ за маршрутом 1** - их `ROUTE` никто
   не переписывает. Логика: на общем участке маршруту 2 нужен только
   ПРОВОД, сами опоры уже посчитаны в проекте 1 (или существующие,
   тогда вообще не считаются). Если когда-нибудь понадобится иначе -
   отдельная задача, менять придётся XDATA самих опор.
2. **Допуск 1 м завышен сознательно** (опоры-то ставятся проекцией
   ТОЧНО на трассу): полилинию второго маршрута пользователь рисует
   РУКАМИ поверх уже стоящих опор, и если вести "на глаз" без
   привязки - промах в десятки сантиметров реален. Слишком маленький
   допуск в этом случае просто не увидел бы маршрут 2 кандидатом, и
   пролёт молча ушёл бы в маршрут 1 - это хуже, чем лишний вопрос.
   **Рекомендация при работе**: рисовать маршрут 2 с привязкой к точкам
   вставки опор (или хотя бы не промахиваться больше метра).

## ✅ Новые нормы запаса длины + труба для ГНБ-прокола (2026-07-24)

### 1. Что изменилось в числах

«сырая + 6 м», так и показывает. Подробно — пункт 4 ниже.

### 2. Общая формула теперь одна на оба типа линии

`LEP:GetRealLength` (`LEP-SPAN.LSP`) переписана с двух отдельных веток
на одну формулу с разными слагаемыми:

```
( база + фикс.добавка ) × ( 1 + процент/100 ) × число_фаз
```

- **ВЛ**: фикс. добавки нет, процент `*LEP-Sag-VL*`, фаз 3 или 1;
- **КЛ**: фикс. добавка +6 м, процент по способу прокладки, фаз всегда 1.

Сигнатура выросла с двух аргументов до четырёх —
`(TypeCode Method VClass SpanLength)`: формула теперь зависит ещё и от
способа прокладки (`METHOD` из XDATA, ГНБ/траншея), и от класса
напряжения маршрута (`VCLASS`). Единственное место вызова —
`C:LEP-SPAN`, там обе переменные уже были в области видимости, новых
запросов пользователю не появилось.

### 3. Почему проценты КЛ идут ПОВЕРХ +6 м, а не вместо них

Это была главная развилка, спросил у пользователя отдельно. Ответ —
**поверх**, и вот почему это не двойной запас:

- **+6 м** — это НЕ запас на закупку, а **реальная физическая длина**
  кабеля, который лезет по 3 м на каждую из двух опор (уточнено
  пользователем ещё 2026-07-22, записано в шапке
  `LEP:FinalizeSpanLabel`);
- **процент** — запас на укладку «змейкой» и неровности трассы.

Разные величины → складываются: `(L + 6) × 1.02`.

**Эти проценты на чертеже не видны** — см. пункт 4 ниже.

### 4. ⚠️ Чертёж и ведомость показывают РАЗНЫЕ числа (и это правильно)

Формулировка пользователя от 2026-07-24, окончательная:

> Кабель и провод на чертеже показываешь без запаса (только подъём +6
> остаётся). Все запасы идут только в ведомость.

Отсюда — **две разные функции, которые легко перепутать**:

| Функция | Что считает | Куда идёт |
|---|---|---|
| `LEP:GetDisplayLength` | ВЛ — сырая длина; КЛ — сырая + 6 м на каждый пролёт | подпись на чертеже |
| `LEP:GetRealLength` | всё вышеперечисленное + процент запаса + множитель фаз | XDATA `LENGTH` → ведомость |

Почему у кабеля +6 м остаётся и на чертеже: это **не запас**, а реальный
кусок кабеля, который физически лезет по 3 м на каждую из двух опор.
Провис провода — наоборот, чистый запас на закупку, на плане провод
нарисован по трассе, и подпись должна совпадать с тем, что человек
видит и может померить линейкой.

⚠️ Множитель фаз (×3 у 10/6 кВ) на чертеж **не попадает вообще** — иначе
подпись «95 м» на пролёте в 30 м выглядела бы как ошибка черчения.

⚠️ Техническая деталь: `LEP:FinalizeSpanLabel` теперь **не заглядывает в
XDATA `LENGTH` вообще** — обе величины подписи считаются от `RAWLENGTH`.
Побочный эффект: округление до целого метра делается один раз на всю
группу пролётов, а не отдельно у каждого — число может отличаться от
старого на метр-два, это честнее (меньше накопленных «хвостиков»).

### 5. Почему ×3 у высокого напряжения и почему только у провода

У 10/6 кВ провод СИП-3 — на каждую фазу идёт **отдельный** провод,
значит на один пролёт нужно три длины. У 0,4 кВ провод СИП-2 — все
жилы уже в одном жгуте, множитель 1. Множители — в
`*LEP-Phases-ByClass*`, ключи те же, что коды в `*LEP-VoltageClasses*`
(`"10"`/`"6"`/`"04"`).

⚠️ **К КЛ множитель не применяется никогда, даже на 10 кВ**: кабель
10 кВ трёхжильный — это одна строительная длина, а не три. Именно
поэтому `LEP:GetPhaseCount` принимает и тип линии, и класс, а не только
класс.

⚠️ **6 кВ тоже ×3** (подтверждено пользователем 2026-07-24) — провод
там тот же СИП-3.

⚠️ Если класс не найден в `*LEP-Phases-ByClass*` — возвращается 1.
Осознанно осторожный вариант: лучше увидеть заниженное число в
ведомости, чем молча утроить длину там, где утраивать не надо. **Если
появится новый класс напряжения — не забыть добавить строку в
`*LEP-Phases-ByClass*`.**

### 6. Округление — один раз, в самом конце

Порядок важен: `вверх(L × 1.045 × 3)`, а НЕ `вверх(L × 1.045) × 3`.
Прямая формулировка пользователя — «умножаем на 3 после прибавления
запасиков». Если округлять каждую фазу отдельно, мы бы трижды
докидывали «хвостик» округления и завышали ведомость.

### 7. Труба для ГНБ-прокола — новая позиция ведомости

Кабель ГНБ тянут внутри пластиковых труб, которые закупают отрезками по
13 м. Это **отдельный материал**, никак не связанный с метражом самого
кабеля. Формула:

```
труб на прокол = ( вверх( длина_прокола / 13 ) + 1 ) × 2
```

Константы — `*LEP-GNB-PipeLength*` (13.0), `*LEP-GNB-PipeSpare*` (1),
`*LEP-GNB-PipesPerBore*` (2), название строки —
`*LEP-Label-GNB-Pipe*` (длина отрезка подставляется в название
автоматически, чтобы название не разъехалось с константой).

Считает **ЭТАП 1.7** в `LEP-REPORT.LSP` — свой отдельный `ssget` по
слою `*LEP-Layer-Proj-KL-GNB*`, а не общий скан ЭТАПА 1: слой
проектируемой ГНБ-КЛ отдельный (появился 2026-07-22 вместе с выбором
способа прокладки), так что сам факт нахождения объекта на этом слое —
уже готовый признак «это ГНБ и это проект».

**Длина берётся СЫРАЯ** (`RAWLENGTH`, геометрия по плану), не `LENGTH`:
в `LENGTH` уже сидят +6 м на подъём кабеля и процент на укладку — к
длине трубы это отношения не имеет, трубу кладут по факту трассы
прокола. Если `RAWLENGTH` нет (старый пролёт) — откат на `LENGTH`,
чтобы не получить ноль труб на реальном проколе.

### 8. ⚠️ Что считается ОДНИМ проколом (и почему это важно)

⚠️ **ПЕРЕПИСАНО 2026-08-03** — правило поменялось целиком, старая
версия этого раздела больше не действует. Полный разбор, почему
пришлось менять, — ниже в разделе «✅ Два прокола подряд считались
одним».

**ТЕПЕРЬ: один прокол = один пролёт ГНБ.** Запасная труба (+1)
добавляется каждому пролёту ГНБ отдельно, никакой группировки нет.

Обоснование (решение пользователя, «вариант А»): прокол физически не
может пройти **сквозь** объект, стоящий на его конце. У опоры кабель
поднимается наверх (программа сама закладывает на это 3 м с каждого
конца), у маркера точки разрыва бур выходит из земли и заходит заново,
у КТП/киоска кабель заводится внутрь. Любой конец пролёта — это место,
где прокол кончается. Значит пролёт и прокол — одно и то же.

⚠️ **Цена решения, принятая сознательно**: если прокол реально идёт
одним куском мимо промежуточной опоры (кабель не поднимается), он всё
равно посчитается как два — одна лишняя запасная труба. Завысить на
трубу безопаснее, чем недодать: недостача останавливает работы,
излишек лежит на складе.

Строки разных проколов одной трассы складываются в одну позицию
ведомости автоматически — это делает `LEP:AddToMasterList` (та же
позиция, те же единицы). Отдельный накопитель `LEP:AddToBoreList`,
который копил длину прокола из нескольких пролётов, **удалён из
файла** — см. историю git, если групповой подсчёт понадобится вернуть.

<details>
<summary>Как было до 2026-08-03 (для истории)</summary>

Признаком «это один прокол» была **общая подпись** (`LABELHANDLE` в
XDATA): подписи соседних однородных пролётов и так объединяются в одну
(`LEP:FinalizeSpanLabel`), и объединяются по тем же условиям, что
казались нужными здесь — идут подряд, та же марка, тот же статус, та
же трасса. Логика «один прокол = одна общая подпись» продержалась
ровно до первого чертежа с двумя проколами под разными углами.

### 9. ⚠️ Старые пролёты не пересчитываются

`LENGTH` замораживается в XDATA в момент создания пролёта — смена
констант в CONFIG **не пересчитывает уже нарисованные пролёты**. Это не
новость (так было со всеми константами запаса и раньше), но с новыми
нормами разница стала заметной. Пользователь всё равно перерисовывает
чертёж с нуля (решение 2026-07-24 по итогам разбора старого чертежа),
так что вопрос миграции не стоит.

## ✅ Кабельный киоск (КК) и кабель без опор (2026-07-24)

Пользователь принёс схему, которой программа до этого дня не умела:
**из КТП выходят два кабеля 0,4 кВ, идут до участка заявителя, а там
стоит просто кабельный киоск с двумя приборами учёта.** Ни одной опоры
на всём участке. МТП не нужна.

Раньше кабельный пролёт можно было построить ТОЛЬКО между двумя
опорами — `LEP:PickPole` отсеивал всё, у чего `TYPE` ≠ `"POLE"`.

### 1. Почему это оказалось дёшево

КТП (а теперь и киоск) ставится **тем же способом, что и опора**:
`LEP:InsertVertexOnRoute` — проекция клика на трассу, новая вершина,
`GEOMCONSTRAINT`. То есть с точки зрения пролёта это такой же блок на
вершине маршрута, со своим хендлом и своим `ROUTE` в XDATA. Вся
остальная механика (нарезка по вершинам, объединение подписей,
параллельный сдвиг, размерная линия, трубы ГНБ) работает по **хендлам и
вершинам** и о типе объекта не спрашивает вообще.

Поэтому основная правка — одна строка: `LEP:PickPole` теперь принимает
`TYPE` ∈ `POLE`/`KTP`/`KK`.

### 2. Новый объект — кабельный киоск (КК)

- `LEP-KKSYM.LSP` (новый модуль) — блок-символ, **простой
  прямоугольник без значка внутри** (решение пользователя: в киоске
  трансформатора нет, рисовать внутри нечего — в отличие от КТП с её
  треугольником). Устроен по образцу `LEP-KTPSYM.LSP`.
  ⚠️ Размер **1×2 м — прикидка**, ровно как было у КТП с 3×5 («дальше
  допилим»).
- Пункт «КК (кабельный киоск с ПУ, без опоры)» в `LEP-END`.
- Свободный ввод номера (**может быть пустым** — не у каждого киоска он
  есть; подпись тогда собирается без висящего дефиса) и количества ПУ.
- **Слой — тот же `*LEP-Layer-Proj-TP*`/`*LEP-Layer-Exist-TP*`, что у
  КТП.** Отдельный слой не заводили: ведомость различает их по ключу
  `TYPE` в XDATA, а не по слою — причём проверка `TYPE` в ЭТАПЕ 2.6
  стояла там **с самого начала**, поэтому киоск встал на готовый слой
  без единой правки в `LEP-SETUP`.

**Приборы учёта отдельными объектами НЕ рисуются** — внутри киоска они
на плане ничем не отличаются друг от друга. Хранится только их число
(ключ `PUCOUNT`), в ведомость идёт строкой «ПУ» в штуках — тем же
названием `*LEP-Label-PU*`, что и ПУ на опоре: это один и тот же прибор,
для закупки важно общее количество. При нуле строка не выводится вовсе
(киоск без ПУ — реальная вещь).

### 3. Запас КЛ стал ПОКОНЦОВЫМ

Была одна константа `*LEP-KL-Reserve*` = 6 м на пролёт («по 3 м с каждой
стороны на подъём кабеля на опору»). Пока оба конца всегда были
опорами — верно. В новой схеме **не опора ни один конец**: из наземной
КТП кабель выходит внизу и в киоск заходит внизу, лезть ему некуда, и
жёсткие 6 м стали бы чистым завышением на каждом таком пролёте.

Теперь метры начисляются **за каждый конец отдельно**, по типу того,
что на конце стоит (`LEP:GetEndReserve`):

| Концы пролёта | Запас |
|---|---|
| опора — опора | 6 м (как было, ничего не изменилось) |
| КТП — опора | 3 м |
| КТП — киоск | 0 м |

Константы: `*LEP-KL-Reserve-Pole*` (3.0) и `*LEP-KL-Reserve-Ground*`
(**0.0**).

⚠️ **Ноль у наземных — осознанный, а не забытое значение.** Прямое
решение пользователя: «пока запас 0, но константу введи на будущее».
Константа заведена именно для того, чтобы, когда понадобится заложить
слабину на разделку в ячейке КТП или в киоске, это была правка одного
числа, а не поиск по коду.

⚠️ **Неизвестный `TYPE` трактуется как ОПОРА, а не как ноль.** До
2026-07-24 концом пролёта могла быть только опора — значит при сомнении
мы воспроизводим прежнее поведение, а не молча обнуляем запас.

Посчитанное число пишется в XDATA пролёта (ключ `RESERVE`) **при
создании** — потом, при пересчёте общей подписи группы, самих объектов
концов уже нет под рукой, а складывать запасы разных пролётов надо.
Поэтому `LEP:GetDisplayLength` принимает теперь **готовую сумму
запасов**, а не «число пролётов × константа»: у разных пролётов одной
группы запас может отличаться (КТП—опора 3 м, следующий опора—опора
6 м).

⚠️ **Ловушка, на которую чуть не наступили:** `LEP:SetSpanLabelHandle`
вызывается после **каждого** объединения подписей, то есть почти сразу
после создания пролёта. Забыть в ней `RESERVE` — и ключ стирался бы
через секунду после записи (`LEP:SetData` перезаписывает XDATA целиком),
а подпись молча откатывалась бы на запасное «две опоры» у всех пролётов
подряд. Добавлено и туда, и в `LEP:ReassignSpanRoute`.

### 4. ⚠️ Найденный по дороге баг: параллельные близнецы сливались

Объединение подписей задумано для пролётов, идущих **цепочкой** —
они делят ровно **один** общий конец, и сложить их длины правильно. Но
`LEP:GetSpanNeighbors` считает соседом любого, кто делит **хотя бы
один** хендл. Под это определение попадает и **второй кабель между той
же парой концов**: у него совпадают **оба** хендла, а марка и статус,
как правило, те же.

Результат был бы такой: два кабеля по 30 м от КТП до киоска слились бы
в одну подпись «60 м» — как будто проложили один длинный кабель. Тот же
баг ждал и два провода на одной паре опор; механику параллельного сдвига
(2026-07-22) вживую так и не прогнали, поэтому он до сих пор не всплыл.

Исправлено: сосед, у которого совпадают **оба** конца (в любом
порядке — пролёт мог быть нарисован с другой стороны), из группы
объединения исключается. Каждый получает свою подпись — это физически
разные кабели, их и заказывают, и монтируют отдельно.

### 5. ⚠️ Заодно починена высокая сторона КТП

Вторая строка подписи КТП имеет формат «мощность/ВН/НН», и класс высокой
стороны раньше брался **из класса маршрута**, на котором стоит КТП. Пока
КТП ставили на 10-кВ трассу, это случайно совпадало.

Но КТП — это **граница двух классов**: на входе 10 или 6 кВ, на выходе
0,4 кВ. В новой схеме трасса от КТП к киоску — 0,4 кВ, и подпись выдала
бы мусор **«160/04/0,4 кВ»**: и сырой код класса вместо читаемого «0,4»,
и логически неверно — высокая сторона к классу этой трассы отношения не
имеет.

Теперь высокая сторона — отдельный вопрос при постановке КТП
(`*LEP-KTP-HighSide*`, 10/6 кВ), хранится своим ключом `HIGHSIDE`.

### 6. «+ подъём кабеля по опоре» — теперь только на опорах

`LEP:AddKLPoleNote` проверяет `TYPE = "POLE"`. ⚠️ Проверка нужна была
**сейчас**, хотя сегодня она ничего не меняет: у КТП/киоска в XDATA нет
`LABELHANDLE`, поэтому функция и так молча ничего не делала. Но это
**везение, а не замысел** — как только у них появится `LABELHANDLE` (а
он нужен, иначе подпись осиротеет при удалении, ровно как было с
опорами), на наземной подстанции вылезла бы фраза про подъём по опоре.

### 7. Как чертить эту схему

1. `LEP-ROUTE` — трасса 0,4 кВ от КТП до участка.
2. `LEP-END` → КТП (статус «Сущ.», если подстанция уже стоит), высокая
   сторона 10 или 6 кВ.
3. `LEP-END` → КК, номер и «2» приборов учёта.
4. `LEP-SPAN` дважды: клик по КТП, клик по киоску. Второй кабель сам
   сдвинется параллельно на 0,5 м и получит **свою** подпись.

## ✅ Точка смены способа прокладки (2026-07-24)

⚠️ **С 2026-08-03 пункт меню называется «Точка разрыва участка КЛ
(смена способа ИЛИ новый прокол)»** — смысл маркера оказался шире, чем
задумывался, см. раздел «✅ Два прокола подряд считались одним» ниже.
Ниже по этому разделу маркер местами всё ещё называется «точкой смены
способа прокладки» — это его первоначальное, более узкое назначение.

Случай пользователя: трасса от КТП идёт под углом 90°, **первый участок
надо пройти ГНБ (проколом), второй — обычной траншеей**.

Упёрлись в настоящее ограничение: способ прокладки спрашивается **один
раз на пролёт**, а пролёт задаётся **двумя объектами**. В углу объекта
нет — делить не на чем. Поставить туда опору нельзя: её посчитала бы
ведомость, а физически опоры там нет.

### Решение — маркер-пустышка

Новый объект: **точка смены способа прокладки** (`LEP-TRANSSYM.LSP`),
кружок Ø0,5 м. Ставится на трассу тем же механизмом, что КТП и киоск
(проекция клика + вершина + `GEOMCONSTRAINT`), дальше чертятся два
обычных пролёта: КТП → маркер (ГНБ), маркер → киоск (траншея).

Единственный смысл объекта — быть точкой, за которую можно зацепить
концы двух пролётов. Никакой сметной нагрузки он не несёт.

- **Слой непечатаемый** (`LEP-TRANSITION`, `LEP:SetLayerNoPlot`) —
  прямое требование пользователя: «кружок не выводится на печать или
  PDF». Тот же приём, что у служебной линии маршрута и GPS-кружков.
- **Подписи нет сознательно** — она рисовалась бы на печатаемом
  текстовом слое и полезла бы в PDF, ровно то, чего просили избежать.
  И не нужна: где кончается прокол, видно по смене цвета линии —
  участки ГНБ и траншеи лежат на разных слоях.
- **В ведомости не учитывается** — не материал, кабель в этой точке не
  разрезается. Отдельных действий не потребовалось: ведомость сканирует
  конкретные слои, а этого слоя в её списках просто нет.
- **Статус не спрашивается** — маркер не бывает «проектируемым» или
  «существующим».
- Живёт в меню `LEP-END` (отдельную команду не заводили — «команд и так
  хватает»), поэтому запрос переименован с «Тип оконечного
  оборудования» на нейтральное «Что ставим на маршрут»: маркер стоит
  посреди трассы, оконечным оборудованием он не является.

### ⚠️ Почему это блок, а не просто кружок

`CIRCLE` подошёл бы: у него группа DXF 10 — центр, `LEP:PickPole`
достал бы точку так же, как достаёт точку вставки блока. Но `PickPole`
проверяет, что объект — именно `INSERT`, и это полезный инвариант:
**любой конец пролёта — блок с XDATA**. Пока он держится, туда
физически не может попасть линия подосновы или обрывок чужой геометрии.
Ради одного кружка ломать инвариант невыгодно.

### ⚠️ Две ловушки, обе учтены

**1. Запас кабеля у маркера должен быть НОЛЬ.** Кабель в этой точке не
заканчивается, концевой заделки нет. `LEP:GetOneEndReserve` перечисляет
то, у чего запаса нет, а всё остальное считает опорой — забудь там
`"TRANS"`, и маркер молча получил бы 3 м «на подъём по опоре». Причём
ошибка была бы **двойной**: лишние 3 м у конца первого пролёта и ещё
3 м у начала второго.

**2. Найдена и закрыта дыра в объединении подписей.** В шапке проверки
с самого начала было написано «тип прокладки не меняется», но
сравнивались только **марка и статус**. Для пары ВЛ/КЛ этого хватало
случайно — марки провода и кабеля не совпадают текстом. А ГНБ и
траншея — это **одна и та же марка кабеля**, и два соседних пролёта
«прокол, потом траншея» слиплись бы в одну подпись с общей длиной. То
есть мы бы поделили участок, а программа тут же склеила бы его обратно —
и одна подпись висела бы поверх двух линий разного цвета на разных
слоях. Теперь в условие добавлен `METHOD`.

У ВЛ и у существующей КЛ ключа `METHOD` в XDATA нет вообще — с обеих
сторон `nil`, а `(= nil nil)` в AutoLISP даёт истину, поэтому для них
ничего не изменилось. `METHOD` читается из XDATA самого пролёта, а не
передаётся аргументом — так он доступен и при ремонте подписей
(`LEP-SPAN-REPAIR`), где никакого «текущего выбора пользователя» нет.

### Как начертить участок ГНБ + траншея

1. `LEP-END` → «Точка разрыва участка КЛ», клик в углу трассы
   (маркер сядет ровно в существующую вершину — защита от дублирующих
   вершин `*LEP-Vertex-Snap-Tolerance*` сработает сама).
2. `LEP-SPAN`: КТП → маркер, КЛ, способ **ГНБ**.
3. `LEP-SPAN`: маркер → киоск, КЛ, способ **Траншея**.

Трубы посчитаются только на первом участке, подписи останутся
раздельными.

По просьбе пользователя («проверь, чтобы у всех подписей стоял флаг
background mask и draworder front») прошёл по всем местам проекта, где
создаётся текст. Их ровно восемь:

| Что создаёт текст | Фон под текстом | Наверх (draworder) |
|---|---|---|
| Подпись опоры (`LEP:CreatePoleLabel`) | ✅ было | ✅ было |
| Подпись маршрута (`LEP:CreateRouteLabel`) | ✅ было | ✅ было |
| Подпись пролёта (`LEP:CreateSpanLabel`) | ✅ было | ✅ было |
| Подпись КТП (`LEP:CreateKtpLabel`) | ✅ было | ✅ было |
| Подпись киоска (`LEP:CreateKkLabel`) | ✅ было | ✅ было |
| **Размерная линия пролёта** (`DIMALIGNED`) | ❌ **не было → исправлено** | ✅ было |
| **Подпись геоточки** (`TEXT`) | ⚠️ невозможно | ❌ **не было → исправлено** |
| Кружок геоточки (`CIRCLE`) | — не текст | ❌ **не было → исправлено** |

### Дырка 1: у размерных линий не было фона под числом

У всех выносок `MLEADER` фон ставится с 2026-07-15
(`LEP:SetMLeaderBackgroundMask`, вызывается после каждого `_.MLEADER`).
А у размерных линий пролёта системная переменная **`DIMTFILL` не
выставлялась нигде** — держался дефолт AutoCAD, `0` = фона нет.

На чистом холсте это незаметно. Поверх геодезической подосновы, где под
размером проходят горизонтали, заборы и контуры зданий, число
становится нечитаемым. `DIMTAD = 1` (текст над линией) от этого не
спасает — он защищает только от **своей** размерной линии.

Исправлено: `*LEP-Dim-TextFill*` = 1 в `LEP-CONFIG.LSP` и
`(setvar "DIMTFILL" ...)` в `C:LEP-SETUP`, рядом с уже стоявшими
`DIMTIH`/`DIMTOH`/`DIMTAD`. Значение 1 = «цвет фона чертежа» — ровно то
же, что у выносок.

⚠️ Как и у выносок, поведение «цвета фона чертежа» **при печати на
белом листе не проверялось** — только на экране. Если вокруг числа
вылезет тёмный прямоугольник, лечится тут же: `DIMTFILL` = 2 и явный
белый в `DIMTFILLCLR`.

### Дырка 2: геоточки уходили под подоснову

Кружки и подписи GPS-точек (`LEP-GEOPOINTS.LSP`) рисовались через
`entmake` вообще без `DRAWORDER`. Особенно неудачно именно здесь:
геоточки нужны ровно для того, чтобы **сверить их с подосновой**, а
подоснова — самый плотный слой на чертеже. Уйдя под неё, кружок теряет
весь смысл.

Исправлено: `LEP:BringToFront` после каждого `entmake` (и на кружок, и
на подпись). `entmake` возвращает список, а не имя объекта, поэтому
объект берётся через `(entlast)`.

⚠️ **Фон под текстом геоточки поставить нельзя** — это сущность `TEXT`,
у неё фоновой маски не существует в принципе (это свойство `MTEXT` и
`MULTILEADER`). Чтобы он появился, надо менять тип объекта на `MTEXT`.
Не делал: точки временные, лежат на непечатаемом слое и стираются одной
командой `LEP-GEOPOINTS-CLEAR`. Если понадобится — правка на пять
минут.

### Что проверено и оказалось в порядке

- Все пять выносок `MLEADER` вызывают и маску, и `BringToFront` сразу
  после создания.
- `LEP:SetMLeaderText` / `LEP:AppendMLeaderText` (правка текста уже
  существующей подписи — «+ проект. ПУ», перенос подписи в
  `LEP-POLE-MOVE`) **маску не сбивают**: они делают `subst` только по
  группе 304, а группы фона (91/141/291/292) не трогают.
- `LEP-SPAN-REPAIR` пересоздаёт подписи через ту же
  `LEP:CreateSpanLabel`, то есть получает и маску, и порядок отрисовки
  автоматически.

## ✅ Размеры по коленам траншеи + траншея объединяется через маркер (2026-08-04)

Пользователь: «траншея в отличии от ГНБ это просто канава, которая
роется или руками, или трактором. Соответственно объединять подпись для
общей длины траншеи можно и нужно, даже если произошла смена участка».

Правильно, и обоснование крепкое: **прокол дискретен** (вышел бур —
кончился прокол, нужна своя запасная труба), **траншея непрерывна** —
её метраж и объём земляных работ не зависят от того, где мы поставили
служебный маркер.

### Но настоящая причина оказалась не в подписях

На вопрос «когда у тебя вообще появляются две соседние траншеи с
маркером между ними» ответ был неожиданный:

> «Поворот траншеи на какой-то угол. Сейчас, если траншея имеет вид
> например молнии, то подпись с указанием длины ставится от первой
> точки до последней… надо показывать каждый участок до вершины, чтобы
> понимать, сколько копать и объёмы».

То есть маркеры на поворотах ставились **не потому, что там граница**,
а чтобы каждое колено стало отдельным пролётом и получило свой размер.
Подписи рвались побочным эффектом.

Проверка по коду показала, где именно проблема:

| Что | Как считалось | Верно? |
|---|---|---|
| Длина в **выноске** (`RAWLENGTH`) | `LEP:GetSpanLength` — **сумма отрезков** вдоль трассы | ✅ да, «молнию» складывает честно |
| **Размерная линия** (`DimDistance`) | `(distance P1Pt P2Pt)` — **прямая** между концами, одна на пролёт | ❌ на «молнии» меньше, чем копают |

Значит лечить надо **размеры**, а не подписи.

### Правка 1 (причина): размер на каждое колено

Новая `LEP:CreateSpanDimensions` (множественное число) рисует размерную
линию между каждой парой соседних вершин пролёта. Для прямого пролёта
поведение не меняется вообще — один участок, один размер, как было.

Следствие, ради которого всё и делалось: **ставить маркер на поворотах
траншеи больше не нужно.** Проблема с разорванными подписями исчезает в
корне, а не лечится правилом.

⚠️ **Пока только для КЛ** — прямое решение пользователя: «пока сделаем
только для КЛ, ВЛ запиши на будущее, это надо тестить отдельно, на это
нет времени». У ВЛ по-прежнему одна размерная линия на пролёт, старым
вызовом `LEP:CreateSpanDimension`. Формально посегментные размеры и для
ВЛ ничего бы не сломали (у прямого пролёта результат тот же), но вживую
не проверено.

⚠️ Длина каждого участка округляется **отдельно** — это независимые
размеры, каждый должен быть верен сам по себе. Из-за этого сумма
подписанных колен может разойтись с общей длиной в выноске на
метр-другой (несколько округлений вместо одного). Это нормально и
неизбежно для любых размеров на чертеже.

### Правка 2 (правило): траншея объединяется через маркер

Инвариант от 03.08 сужен:

> **Через маркер `TRANS` не объединяется ГНБ.** Всё остальное
> объединяется по обычным правилам (совпали марка, статус, способ).

Способ читается у самого нового пролёта (`ExcludeEnt` в
`LEP:GetSpanNeighbors` — это всегда он). Проверять обе стороны не
нужно: соседа с другим способом и так отсеет сравнение `METHOD` в
`LEP:FinalizeSpanLabel`.

Возможность **принудительно** разделить две траншеи при этом теряется —
пользователь сказал прямо: «нет, всегда объединять». Если когда-нибудь
понадобится (граница подрядчиков, смена глубины заложения) — вернуться
к варианту «спрашивать при постановке маркера, рвёт он подпись или нет».

### Цена правки

**На ведомость не влияет вообще.** Метраж кабеля в CSV суммируется по
марке независимо от разбивки подписей, трубы ГНБ считаются по пролётам.
Меняется только чертёж: число размерных линий и число подписей.

⚠️ Старые чертежи не перерисовываются. `LEP-SPAN-REPAIR` чинит подписи,
а размерные линии не трогает вообще — у уже начерченных пролётов размер
останется прямым. Такие пролёты надо перечертить.

## ✅ В ведомость идут стойки, а не типы опор (2026-08-03)

Требование коллеги пользователя, дословно:

> «П 23 должна быть. Это опора СВ-95 под 0,4 кВ… Тут получается так,
> что П23 это тип опоры, состоит из одной стойки СВ-95. А23 это тип
> опоры, состоит из двух стоек СВ-95. В спецификации нужно именно
> количество стоек».

То есть в программе были слиты две разные вещи:

- **тип опоры** (П23, А23, УА23…) — конструкция целиком, идёт на
  чертёж и в подпись;
- **стойка** (СВ-95-3, СВ-110-5) — железобетонное изделие, которое
  реально покупают. Одна опора собирается из одной, двух или трёх
  стоек.

Ведомость печатала типы («Опора А23 — 5 шт.»), а закупать по ней
нельзя: в накладной нет позиции «опора А23», есть «стойка СВ-95-3».

### Ключевая мысль: откос — это и есть стойка

Она же и объясняет, почему правка вышла дешёвой. Мы и раньше рисовали
у анкерных/угловых опор 1/2/3 трапеции — главную и откос(ы). **Откос
на чертеже физически и есть вторая (третья) стойка**, просто вкопанная
под углом. Значит «сколько трапеций рисуем» и «сколько стоек покупаем»
— **одно и то же число**.

Поэтому старый список `*LEP-PoleColumns*` («тип → сколько трапеций») не
дополнен вторым списком, а **заменён одним общим справочником**:

```lisp
(setq *LEP-PoleStands*          ; ("тип" "марка стойки" количество)
    '(("П23" "СВ-95-3" 1) ("УП23" "СВ-95-3" 2) ("А23" "СВ-95-3" 2) ...))
```

Из него читают оба: `LEP:GetPoleColumns` (рисование символа) и ЭТАП 2
(ведомость). Держать это в двух списках означало бы однажды поправить
один и забыть другой — на чертеже опора с откосом, в ведомости одна
стойка, и **никаких признаков ошибки**.

### Откуда взяты числа

| Семейство | Стойка | Источник |
|---|---|---|
| П20-3Н / А20-3Н / УП20-3Н / УА20-3Н | СВ-110-5 | спецификации альбома 27.0002 (ВЛЗ 6–20 кВ, СИП-3); совпали с числами, которые уже стояли в программе |
| П23 / УП23 / А23 / УА23 | СВ-95-3 | серия 3.407.1-143 (вариант с подкосами) |
| УП21 / К21 | СВ-110-5 | проект 21.0112 — «опоры **одностоечной** конструкции» |

⚠️ **Шифр не определяет конструкцию однозначно.** Тот же «А23» живёт
минимум в двух альбомах: серия 3.407.1-143 (с подкосом, **2 стойки**) и
проект 25.0017 (одностоечная, с опорно-анкерной плитой, **1 стойка**).
Развилку снял коллега прямым ответом «А-23 — 2 стойки» → взят вариант с
подкосами. ⚠️ Он назвал **только А23**; числа для УП23 (2) и УА23 (3)
взяты по той же серии — стоит переспросить.

Марку 21-й серии (альбом допускает СВ105-5 или СВ110-5) коллега назвал
явно: **СВ-110-5**. Написание «СВ-95-3» / «СВ-110-5» — тоже его
(«СВ-95-3 пишут в наших проектах»); каталоги пишут слитно, но нам важно
то, что уходит в документы заказчика.

### Что в ведомости теперь

Строки типов опор **заменены** на стойки — решение пользователя из трёх
предложенных вариантов. По типам опор ведомость больше не показывает
ничего, эта информация остаётся только на чертеже (подписи опор).

Складываются стойки сами собой, без отдельного накопителя:
`LEP:AddToMasterList` суммирует по совпадению названия строки. 30 опор
П23 плюс 5 опор А23 дают одну строку «Стойка СВ-95-3 — 40 шт.».

⚠️ **СВ-110-5 приходит из двух мест** — от опор 6–20 кВ (семейство
«20-3Н») и от 0,4 кВ (семейство «21») — и сливается в одну строку. Для
закупки это правильно: изделие физически одно и то же. Если понадобится
разделять по классу напряжения — это отдельная правка.

### Два побочных улучшения

**1. Закрыта дырка с УП21 и К21.** Их можно было выбрать при
расстановке опор, но в `*LEP-PoleColumns*` их **не было** — при этом в
комментарии к списку УП21 был подробно *описан* («исключение из логики
У+П = 2 столба, 1 столб, подтверждено пользователем»), и в справочной
таблице этого README он тоже значился. То есть и комментарий, и
документация описывали то, чего в данных не было: держалось на тихом
фолбэке «не нашёл тип — считай 1», который случайно давал верный ответ.
Для стоек такой фолбэк уже не спас бы — марку выдумать неоткуда.

**2. Неизвестный тип теперь кричит.** Если типа нет в справочнике, в
CSV попадает строка `!!! НЕТ В СПРАВОЧНИКЕ СТОЕК: <тип>` и печатается
предупреждение в консоль; опора при этом считается одной штукой, чтобы
не исчезнуть совсем. Логика намеренно **обратна** рисованию: там
неизвестный тип тихо рисуется одной трапецией (неточный чертёж лучше
оборванной команды), а в ведомости молча потерянный материал — худшее,
что программа может сделать: на чертеже всё выглядит нормально, ошибка
всплывёт на стройке.

Заодно из `LEP:WriteMasterListBlock` убрана приклейка префикса
«Опора » по `*LEP-PoleTypes*` — после замены она не могла совпасть
никогда.

## ✅ Два прокола подряд считались одним (2026-08-03)

**Найдено пользователем на живом чертеже.** Ситуация: прокол ГНБ →
точка разрыва → **снова прокол ГНБ, но под другим углом**. Программа
слепила оба в одну подпись, а следом и в один прокол в ведомости.

### Почему так вышло

Объединение подписей (`LEP:FinalizeSpanLabel`) склеивает соседние
пролёты, если совпали **марка, статус и способ прокладки**. У двух
проколов совпало **всё три**: одна марка кабеля, оба проектные, оба
ГНБ. Общий конец у них есть — маркер разрыва. «Близнецами» (два
кабеля между одной парой концов) они не являются — делят один хендл, а
не оба. Значит все условия объединения выполнены.

Ключевая мысль: **два прокола различаются не данными, а физикой** —
бур вышел из земли и зашёл заново под другим углом. Сравнением полей
XDATA это не ловится в принципе, сколько полей ни добавляй.

Дальше эффект домино: ведомость считала проколы по ключу
`LABELHANDLE` (ЭТАП 1.7) — одна подпись = один прокол. Длины
сложились, **запасная труба посчиталась одна вместо двух**.

Отдельно неприятно, что на чертеже это выглядело правдоподобно: одна
подпись с суммарной длиной, никаких признаков ошибки. Поймать можно
было только вручную пересчитав трубы.

### Что сделано — две правки

**1. Маркер `TRANS` стал жёсткой границей объединения**
(`LEP:GetSpanNeighbors`, `LEP-SPAN.LSP`). Если объект, в который
упираются два пролёта, — маркер разрыва, соседями они не считаются
вообще. Новый общий инвариант, который нельзя терять при следующих
правках условий объединения:

> **Маркер `TRANS` = граница участка работ. Через него не объединяется
> НИЧЕГО и никогда.**

Проверка стоит **до** сравнения полей и не зависит от него — именно
потому, что сравнением полей эту разницу поймать нельзя.

⚠️ **ИНВАРИАНТ СУЖЕН 2026-08-04 — читай раздел «Траншея через маркер
объединяется» ниже.** Формулировка выше действовала один день. Теперь
она звучит так: **через маркер `TRANS` не объединяется ГНБ**; траншея
объединяется. Абзац ниже про «побочный эффект» с тех пор описывает не
поведение программы, а ровно ту причину, по которой правило пришлось
менять.

Побочный эффект, принятый сознательно: две соседние **траншеи** с
маркером между ними тоже получат две подписи вместо одной. На метраж
кабеля в ведомости это не влияет (метры суммируются в любом случае),
только на число подписей на чертеже.

⚠️ Мелочь по коду: `handent` с аргументом `nil` **падает с ошибкой**,
поэтому хендл конца сначала проверяется на существование (у пролётов
старше 2026-07-22 его нет вовсе). На несуществующий хендл (маркер
стёрли руками) `handent` вернёт `nil` — это не ошибка, просто граница
не распознается и пролёты поведут себя как раньше.

**2. Прокол = один пролёт ГНБ** (ЭТАП 1.7, `LEP-REPORT.LSP`) — «вариант
А», выбранный пользователем из двух предложенных. Подробнее — в разделе
«⚠️ Что считается ОДНИМ проколом» выше. Вторая правка нужна была
потому, что первая закрывает только случай с маркером: два прокола,
разделённые **опорой**, слиплись бы точно так же — а у опоры кабель
поднимается наверх, то есть это тоже два разных прокола.

### Заодно переименован пункт меню

Было: «Точка смены способа прокладки КЛ (ГНБ ↔ траншея)».
Стало: **«Точка разрыва участка КЛ (смена способа ИЛИ новый прокол)»**.

Старое название описывало единственный случай, ради которого маркер
заводили, и прямо **отговаривало** ставить его там, где способ не
меняется, — а ставить надо. Заодно поправлено сообщение в командной
строке после установки маркера: теперь оно проговаривает, что два
пролёта получат **разные** подписи.

### ⚠️ Уже начерченное само не починится

Правка действует на **вновь создаваемые** пролёты. На текущем чертеже
два слипшихся прокола придётся перечертить. Вариант «стереть общую
подпись и прогнать `LEP-SPAN-REPAIR`» выглядит рабочим (ремонт
переиспользует `LEP:FinalizeSpanLabel` целиком, а та теперь знает про
границу), но **вживую не проверялся** — если пробуешь, сверь результат
глазами.

## ✅ У окончания ПУ свой тип опоры — «П23» (2026-08-03)

Прямое указание пользователя: у окончания **ПУ** опора должна быть типа
**П23**, а не «П20-3Н», как было.

### Почему заведена ОТДЕЛЬНАЯ константа

Соблазн был поправить одну строку — `*LEP-End-PoleType*` в
`LEP-CONFIG.LSP`. Так делать было нельзя: **эта константа обслуживает
всё оконечное оборудование сразу** — и ПУ, и СТП, и все три опоры МТП
(РЛК/МТП/ЩУ). Правка «в одну строку» молча переставила бы тип и у МТП
со СТП, о чём никто не просил, и заметить это можно было бы только
случайно — на чертеже подпись выглядит одинаково правдоподобно с любым
номером опоры.

Поэтому добавлена вторая константа:

```lisp
(setq *LEP-End-PoleType*        "П20-3Н")   ; СТП и все три опоры МТП
(setq *LEP-End-PoleType-PU*     "П23")      ; только ПУ
```

Если окажется, что «П23» нужен и остальным окончаниям — достаточно
поставить его в первую строку, вторая тогда просто продублирует
значение и ничего не сломает.

### Как это устроено в коде

Тип **вычисляется один раз** в переменную `PoleType` сразу после того,
как выбран вид окончания, и дальше по всей команде используется только
она:

```lisp
(setq PoleType
    (if (= EndType "PU") *LEP-End-PoleType-PU* *LEP-End-PoleType*))
```

Так сделано не для красоты. Тип опоры нужен в **трёх** местах: при
вставке блока-символа, в тексте подписи («Проект. оп. П23») и в XDATA
(ключ `MODEL`, из которого потом считается ведомость). Подставляй
константу в каждое место отдельно — достаточно забыть одно, и получится
расхождение «на чертеже стоит один символ, в подписи написано другое, в
CSV попало третье». Такое **глазами на чертеже не видно** — ровно тот
класс тихих ошибок, на котором этот проект уже обжигался (история с
XDATA у КТП, полтора дня без единого байта данных).

### В ведомость новый тип попал сам собой

`LEP-REPORT.LSP` править не пришлось вообще. ЭТАП 2 считает опоры по
ключу `MODEL` в XDATA, а `MODEL` пишет `LEP:AddEquipData` из того же
`PoleType`. Поменялся тип — поменялась и строка ведомости.

⚠️ **Но это работает только при одном условии**, и его надо помнить,
заводя ЛЮБОЙ новый тип опоры. Тип обязан присутствовать в двух списках
`LEP-CONFIG.LSP`:

| Список | Что будет, если типа там нет |
|---|---|
| `*LEP-PoleStands*` | неоткуда взять ни марку стойки для ведомости, ни число трапеций для символа — в CSV попадёт громкая строка «НЕТ В СПРАВОЧНИКЕ СТОЕК» |
| `*LEP-PoleTypes*` | тип нельзя будет выбрать при обычной расстановке опор |

Проверено на 2026-08-03: «П23» есть в обоих, причём в
`*LEP-PoleStands*` со значением `("СВ-95-3" 1)` — одна стойка, то есть
одна трапеция, ровно как у «П20-3Н». Значит **геометрия символа не
изменилась**, поменялись только текст подписи и строка в ведомости.

⚠️ Этот абзац написан ещё до перехода на стойки (в тот же день, но
раньше): тогда в ведомость от опоры ПУ шла строка «Опора П23», теперь —
«Стойка СВ-95-3». Суть правки от этого не поменялась.

### Чего правка НЕ касается

- **«ПУ на существующую опору»** — там новая опора не создаётся вообще,
  тип берётся у уже стоящей.
- **СТП, РЛК, МТП, ЩУ** — по-прежнему «П20-3Н».
- **Обычные опоры `LEP-POLE`** — тип там и так спрашивается у
  пользователя из полного списка.

## ✅ Подписи КТП/КК уезжали на чужой слой (2026-07-24)

**Найдено пользователем на живом чертеже**, первым же прогоном после
добавления точки смены способа прокладки: маркер лёг на
`LEP-TRANSITION` (правильно), символ киоска — на `LEP-PROJ-TP`
(правильно), **а подпись киоска — на `LEP-TRANSITION`** (слой
непечатаемый, значит подпись просто не попала бы в PDF).

Причина двойная, и обе половины стоит понимать отдельно.

### Половина 1 — настоящая причина: подписи КТП/КК не переключали слой

Команда `_.MLEADER` рисует **на текущем слое**, какой бы он ни был.
Подписи опор (`LEP:CreatePoleLabel`), маршрута (`LEP:CreateRouteLabel`)
и пролётов (`LEP:CreateSpanLabel`) текущий слой честно переключают на
нужный и возвращают обратно. А `LEP:CreateKtpLabel` — **не переключала
вообще**, с самого появления КТП 2026-07-22. Я скопировал эту функцию
как образец для `LEP:CreateKkLabel` и вместе с ней скопировал дырку.

Баг полтора дня не всплывал **случайно**: после загрузки текущим слоем
оказывался безобидный печатаемый `LEP-MANUAL`, подпись выглядела
нормально, и заметить это можно было только через диспетчер слоёв.

Исправлено: обе функции теперь сохраняют `CLAYER`, ставят
`*LEP-Layer-Text*` и возвращают старый — как все остальные подписи.

### Половина 2 — почему рвануло именно сейчас

`LEP:CreateLayer` запускает `-LAYER Make` **только если слоя ещё нет**.
А `-LAYER Make` делает созданный слой **текущим** — свойство самой
команды AutoCAD, обойти нельзя.

Отсюда приём «создаём `LEP-MANUAL` последним, он сам станет текущим»
работал **только на пустом чертеже**. На чертеже, где вы уже работали,
все слои существуют, и создаётся ровно один — **новый, только что
добавленный в программу**. Текущим становится он.

Именно это и произошло: появился `LEP-TRANSITION`, стал текущим, и всё,
что рисуется без явного слоя, поехало туда.

Исправлено: `C:LEP-SETUP` теперь выставляет текущий слой **явно**,
последней строкой (`LEP:SetCurrentLayer *LEP-Layer-Manual*`), а не
надеется на побочный эффект порядка создания. Порядок создания оставлен
прежним — он больше ни на что не влияет, но и вреда не приносит.

### ⚠️ Урок на будущее

**Добавление любого нового слоя меняло текущий слой на уже начатых
чертежах.** Это ровно тот класс багов, который проявляется не сразу и
не у того, кто правил код. Теперь защита стоит системно, но правило
остаётся: **всё, что рисуется командой (`_.MLEADER`, `_.PLINE`,
`DIMALIGNED`), обязано явно выставлять свой слой и возвращать
старый** — на `entmake` это не распространяется, там слой задаётся
группой 8 прямо в списке.

### Что делать с уже начерченным

Подпись киоска, которая успела лечь не на тот слой, чинится вручную:
выделить её и в выпадающем списке слоёв перевести на `LEP-TEXT`.
Перечерчивать киоск не нужно.

## ✅ КТП полтора дня жила ВООБЩЕ БЕЗ XDATA (2026-07-24)

**Найдено пользователем:** КТП не выбирается в `LEP-SPAN` ни первым, ни
вторым концом пролёта — а кабельный киоск и кружок-маркер выбираются.

### Причина — не там, где искали

`LEP:PickPole` ни при чём. У КТП на чертеже **не было ни байта XDATA**,
поэтому `TYPE` читался как `nil` и объект не проходил проверку.

`LEP:SetData` собирает XDATA через `strcat`, а `strcat` принимает
**только строки**. `LEP:AddKtpData` передавала мощность **числом** —
она приходит из `getreal` в `C:LEP-END`. Запись падала с `bad argument
type` **посреди работы**, XDATA не записывалась вообще, а КТП оставалась
на чертеже выглядящей совершенно нормально: символ нарисован, подпись
есть, констрейнт держит.

Так с **2026-07-22**. Полтора дня незамеченным, потому что:

- симптомов на чертеже нет вообще;
- в ведомость КТП не попадала (ЭТАП 2.6 проверяет `TYPE = "KTP"`) — но
  ведомость с КТП живьём ни разу не выгружали;
- концом пролёта КТП стала только 2026-07-24 — вот тогда и вылезло.

Киоск и маркер работали именно потому, что у них **все** значения
строки (`PUCOUNT` пишется через `itoa` сразу при вызове).

### Исправлено в двух местах

**1. Источник** — `LEP:AddKtpData` пишет `(rtos Power 2 0)`. Формат
такой же, как в подписи КТП, чтобы число в XDATA и число на чертеже
совпадали ровно, без хвоста `,000`.

**2. Страховка в `LEP:SetData`** — числа теперь молча приводятся к
строке (`rtos`/`itoa`). Это **не разрешение передавать числа**: у
вызывающей стороны больше контекста (сколько знаков имеет смысл),
поэтому правильнее делать `rtos`/`itoa` у себя. Страховка нужна ровно
для того, чтобы следующая такая описка стоила неверного формата числа,
а не **молча потерянных данных объекта**.

⚠️ `nil` СОЗНАТЕЛЬНО не превращается в пустую строку, а пропускает ключ
целиком (с громким предупреждением в командной строке). Причина: в
AutoLISP **пустая строка — истина**, и проверки вида
`(if (LEP:GetDataValue E "RESERVE") ...)`, которых по проекту много,
начали бы срабатывать там, где данных на самом деле нет. Пропущенный
ключ читается как `nil` — ровно то, чего эти проверки и ждут.

### ⚠️ Урок

**Значения XDATA в этом проекте — всегда строки.** Число, случайно
попавшее в `LEP:SetData`, не даёт ни ошибки на экране, которую заметишь,
ни видимого дефекта — объект просто тихо остаётся без данных и выпадает
из ведомости и из всех проверок по `TYPE`. Проверено: остальные вызовы
(`AddRoute`/`AddPoleData`/`AddEquipData`/`AddKkData`/`AddTransData`,
пролёты в `LEP-SPAN`) передают строки.

### Что делать с уже начерченной КТП

Данные ей уже не приписать — их там нет. Проще всего стереть символ КТП
вместе с подписью и поставить заново командой `LEP-END` (перед этим
перезагрузить модули). Вершина маршрута под ней останется — это
безвредный хвостик, и при повторной постановке в ту же точку она будет
переиспользована (защита `*LEP-Vertex-Snap-Tolerance*`).

## ✅ Третья строка подписи КЛ — способ прокладки (2026-07-24)

По просьбе пользователя у подписи кабельного пролёта появилась ещё одна
строка внизу:

- ГНБ — **две строки**: «2 трубы 160 мм» / «методом ГНБ»
  (у подписи КЛ они идут третьей и четвёртой);
- траншея — одна строка **«в траншее»**.

CONFIG**, а не пишутся текстом: иначе подпись на чертеже разъехалась бы
с ведомостью при первой же правке числа труб. Диаметр в расчёте
количества труб не участвует вообще — он нужен только для этой надписи.

Форма слова «труба» считается по правилу русского языка
(`LEP:PluralPipes`: 1 труба, 2–4 трубы, 5–20 труб, 11–14 — исключение).
Сейчас труб всегда 2 и можно было бы написать «трубы» текстом — но
константа на то и константа, что её однажды поменяют, и подпись молча
стала бы безграмотной.

**Строка появляется только у ПРОЕКТИРУЕМОЙ КЛ.** У ВЛ и у существующей
КЛ ключа `METHOD` в XDATA нет (у существующей способ прокладки не
спрашивается — она уже проложена как проложена), `LEP:GetMethodLabel`
вернёт `nil`, и подпись останется двухстрочной, ровно как была.

⚠️ Подпись общая на группу соседних пролётов — но накрыть участок с
другим способом прокладки она физически не может: в тот же день
`METHOD` вошёл в условие объединения групп (см. раздел про точку смены
способа прокладки выше).

⚠️ Текст ГНБ разбит на **две строки** (уточнение пользователя в тот же
день; первая версия была одной строкой). Разрыв — код абзаца MTEXT
`\P`, а не `\n`: это `MLEADER`/`MTEXT`, у них свой код переноса — тот
же приём, что и во всех остальных многострочных подписях проекта.

## ✅ Опоры из `LEP-END` не помнили свою подпись (2026-07-28)

**Как поймали.** Пользователь начертил кабельный пролёт, одним концом
которого была обычная опора, а другим — опора с ПУ, поставленная
командой `LEP-END`. К обычной опоре фраза **«+ подъём кабеля по опоре»**
дописалась, к опоре с ПУ — нет. Никакой ошибки в консоли при этом не

(`LABELHANDLE`) — подпись это отдельный объект `MLEADER`, никак не
связанный с блоком опоры средствами AutoCAD. У обычных опор этот ключ
пишется с 2026-07-15 (`LEP:AddPoleData` получила тогда параметр
`LabelEnt`). А вот у `LEP:AddEquipData` — функции, которой пишутся данные
ВСЕХ опор из `LEP-END` (ПУ/СТП/РЛК/МТП/ЩУ), — такого параметра просто не
завели: правку 2026-07-15 сделали в одной функции из двух. Подпись
создавалась как надо, но ename, который возвращает
`LEP:CreatePoleLabel`, в `C:LEP-END` **выбрасывался**, и в XDATA опоры
ключа `LABELHANDLE` не появлялось вообще. Не найдя ключа,
`LEP:AddKLPoleNote` молча ничего не делает — по построению, без ошибки
(так и задумано: она же вызывается и на КТП/киоске, где подписи про
подъём быть не должно).

**Что исправлено.**

- `LEP:AddEquipData` (`LEP-DATA.LSP`) получила шестым параметром
  `LabelEnt` и пишет `LABELHANDLE` — ровно как `LEP:AddPoleData`. Если
  `LabelEnt` = `nil`, ключ просто не пишется (`LEP:SetData` пропускает
  `nil`-значения) — то есть старое поведение остаётся доступным.
- Все пять мест в `C:LEP-END` (`LEP-END.LSP`) теперь запоминают
  результат `LEP:CreatePoleLabel` и передают его дальше: ПУ, СТП, РЛК,
  МТП, ЩУ.
- У МТП `LABELHANDLE` записан **опоре 2**, хотя выноска указывает на
  середину между опорами 2 и 3: подпись относится именно к этой опоре, на
  неё же записан МТП в ведомости.

**Побочно закрыта вторая дырка, которую ещё не замечали:**
`LEP-POLE-DELETE` не удалял подпись таких опор — искать её было нечем, и
после удаления опоры с ПУ надпись оставалась висеть в воздухе. Теперь
удаляется вместе с опорой.

## ✅ `LEP-POLE-MOVE` обеднял опору при переносе (2026-07-28)

Вылезло следом за предыдущим пунктом, при разборе того же кода.

**В чём была беда.** Перенос устроен как «удалить старую опору +
поставить новую на новом месте» (`LEP:DeletePoleGroup` +
`LEP:PlacePoleOnRoute`). Со старой опоры при этом переносились только
**тип и статус** — их команда честно вычитывала из XDATA до удаления. Всё
остальное терялось, потому что `LEP:PlacePoleOnRoute` — это обычная
постановка обычной опоры, она про надстройки ничего не знает:

- **ключ `EQUIP`** (ПУ / СТП / РЛК / МТП / ЩУ). Опора переставала быть
  опорой с оборудованием, и это оборудование **пропадало из ведомости** —
  `LEP-REPORT` считает его именно по `EQUIP`. Молча, без единой ошибки:
  на чертеже стоит та же трапеция, в CSV строки нет;
- **текст подписи**. Новая собиралась стандартная — «[статус] оп. [тип]»
  + класс напряжения. Исчезало всё, что было дописано сверх этого:
  «ПУ», «+ проект. ПУ» (оборудование на существующей опоре), «+ подъём
  кабеля по опоре» (конец кабельного пролёта), «+ СТП-XX кВА».

**Как исправлено.** До удаления запоминаются `EQUIP`/`EQUIPSTATUS` и
**полный текст старой подписи**, после вставки новой опоры всё это
возвращается на место:

- текст ставится старый **целиком** (`LEP:SetMLeaderText`), а не
  собирается заново. Перенос не меняет ни тип, ни статус, ни класс линии
  — значит старый текст остаётся верным до последней буквы. И собрать его
  заново всё равно нельзя: дописанные строки нигде в XDATA не хранятся,
  они существуют только в самом тексте подписи;
- `EQUIP`/`EQUIPSTATUS` дописываются в XDATA новой опоры через
  `LEP:AddEquipToExistingPole` — ту самую функцию, которая умеет добавить
  оборудование, не затирая `TYPE`/`ROUTE`/`MODEL`/`STATUS`/`LABELHANDLE`
  (обычная `LEP:AddEquipData` снесла бы только что записанный
  `LABELHANDLE` новой подписи).

Заодно из `LEP:AppendMLeaderText` выделены `LEP:GetMLeaderText` /
`LEP:SetMLeaderText` (`LEP-UTILS.LSP`) — работа с группой DXF 304 и всеми
её ловушками осталась в одном месте проекта, а не расползлась двумя
почти одинаковыми кусками.

⚠️ **Предел возможного:** если у старой опоры не было `LABELHANDLE`
(поставлена до фикса из предыдущего пункта), переносить текст неоткуда —
подпись получится стандартная, новая. Данные об оборудовании при этом
переносятся нормально, они лежат в XDATA самой опоры.

⚠️ **Осталось как было:** `LEP-POLE-MOVE` работает только с `TYPE =
"POLE"`. КТП и кабельный киоск этой командой не переносятся — она честно
скажет «это не опора». Не трогал: у них своя геометрия и свой набор
полей, переносить их надо отдельной веткой, а спроса на это пока не было.

## ✅ Параллельный сдвиг стал посегментным (2026-08-06)

Продолжение истории про два маршрута с общим участком. Провода
маршрута 2 легли **точно поверх** проводов маршрута 1, хотя механизм
сдвига в программе есть с 22.07.

### Почему не сработало

Сдвиг считался по **совпадению пары хендлов опор**
(`LEP:FindSamePolePairSpans`): сколько уже нарисовано пролётов с теми же
двумя концевыми опорами.

| | Первый конец | Второй конец |
|---|---|---|
| пролёт маршрута 1 | первая опора м1 | ТП |
| пролёт маршрута 2 | первая опора м2 | ТП |

Совпал один хендл из двух, условие требует оба → сдвиг ноль.

Механизм писался под свою задачу — **два провода между одной и той же
парой опор** — и с ней справлялся. Частичное перекрытие он не видит
**в принципе**: умеет отвечать только «та же пара / не та же». Клик
«первая → последняя» тут ни при чём: у маршрута 1 всё равно один
длинный пролёт, и попарный клик по маршруту 2 тоже не дал бы совпадения.

### Как сделано

Перекрытие ищется **геометрически и отдельно для каждого отрезка**
(`LEP:CountOverlappingSpans`), тем же правилом, что и дубли размерных
линий: середина нашего отрезка лежит на чужом отрезке **и** отрезки
параллельны. Сколько чужих пролётов накрыло отрезок — такой у него и
номер сдвига.

Отсюда само собой получается то, что и требовалось: **своя улица
маршрута 2 остаётся на месте, а общий с маршрутом 1 участок уезжает
вбок**. Заодно закрыт случай, до которого мы иначе дошли бы позже:
маршрут 3 может перекрываться с маршрутом 1 на одном куске и с
маршрутом 2 на другом — сдвиг ему нужен разный, и одно число на весь
пролёт этого не умеет.

⚠️ **Каждый чужой пролёт считается один раз**, даже если наш отрезок
накрывает несколько его отрезков сразу. А он накрывает: у маршрута 2
общий участок — один длинный кусок поверх нескольких коротких. Без
этого один сосед насчитался бы за трёх, и провод уехал бы втрое дальше.

### Переход получается плавным сам собой

`LEP:OffsetPointsPerSegment` даёт каждой вершине направление и сдвиг
**её собственного отрезка**. Там, где сдвиг меняется, предыдущий отрезок
становится чуть наклонным, и линия уходит вбок постепенно. Ступеньки не
будет: чтобы её получить, пришлось бы специально вставлять лишнюю
вершину. При 0,3 м на отрезке в десятки метров отклонение меньше
градуса — глазом не читается как излом.

⚠️ **Нормаль своя у каждой вершины.** Старая `LEP:OffsetPointList` брала
один перпендикуляр — к прямой «первый конец пролёта — последний» — и
двигала по нему всё разом. На прямом пролёте разницы нет, но пролёт
маршрута 2 идёт своей улицей и потом сворачивает: общий перпендикуляр
увёл бы линию вбок под углом, и она перестала бы быть параллельной
трассе на обоих кусках сразу. Старая функция оставлена в файле, но
больше не вызывается.

### Два следствия, которые пришлось развести явно

⚠️ **Убрано условие `(= ParallelN 0)` перед рисованием размеров.** Оно
означало «второй провод на этой паре опор размеров не рисует вообще» и
было единственной защитой от дублей до 05.08. С посегментным сдвигом
оно стало вредным: одного перекрытого отрезка хватило бы, чтобы
выключить размеры **на всём пролёте**, включая его собственную улицу.
Теперь решает `LEP:DimensionAlreadyThere` — отдельно по каждому участку.

⚠️ **Размеры и длина считаются по несдвинутой геометрии** (`SubVertsRaw`).
Сдвиг — условность оформления, а размер и метраж — реальность. Пока
сдвиг был одинаковым на весь пролёт, разницы не было: параллельный
перенос не меняет длин. С посегментным отрезок, на котором сдвиг
меняется, становится чуть длиннее — и в ведомость пошла бы длина
оформительской копии.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: (1) пролёт маршрута 2 на
общем участке уезжает вбок, а его собственная улица остаётся на трассе;
(2) переход плавный, без ступеньки; (3) обычный второй провод на той же
паре опор по-прежнему сдвигается, как раньше; (4) размеры стоят по
настоящей трассе, а не по сдвинутой линии; (5) длина в ведомости не
изменилась от сдвига.

## ✅ Размеры дублировались на общем участке двух маршрутов (2026-08-05)

Найдено сразу после предыдущей правки: пролёт маршрута 2 наконец пошёл
по трассе — и расставил размерные линии поверх тех, что уже стояли от
маршрута 1. Причём **где-то задвоилось, а где-то нет**, и это выглядело
случайным.

### Почему дублировались

Единственной защитой от дублей был счётчик пролётов **на той же паре
опор** (`LEP:FindSamePolePairSpans`): размеры рисуются только при
`ParallelN = 0`. У маршрута 1 пролёт «его первая опора → ТП», у
маршрута 2 «его первая опора → ТП». Дальний конец общий, ближний
разный → пара не совпала → счётчик ноль → рисуем всё заново.

### Почему «где-то да, где-то нет»

Размер рисуется на каждый отрезок **между вершинами того маршрута, по
которому идёт пролёт**. У маршрута 1 вершина стоит на каждой опоре —
их туда вставляла постановка опор. У маршрута 2 на общем участке своих
вершин нет вообще (опоры чужие): есть только те, где пользователь
кликал мышкой, когда рисовал полилинию. Отсюда:

- клик при рисовании попал в опору → отрезки совпали → **размер лёг
  ровно поверх старого**;
- вёл линию мимо опор → отрезок длиннее, накрывает несколько старых →
  **размер не совпал, а перекрыл**.

Никакой случайности — всё зависит от того, где стоят вершины второй
полилинии.

### Как исправлено

Проверяем не «чей это пролёт», а **есть ли уже размерная линия на этом
месте**. Так проще и надёжнее: чертёж про маршруты ничего не знает,
размер — это просто объект на слое `LEP-DIM`. Заодно ловятся дубли
внутри одного маршрута.

Перед рисованием размера на участок берём его **середину** и ищем среди
существующих размеров такой, у которого выполнены **оба** условия:

1. середина нового участка лежит на его отрезке (ближе
   `*LEP-Dim-Duplicate-Tolerance*`, 1 м);
2. отрезки параллельны (угол меньше `*LEP-Dim-Duplicate-AngleTol*`, 10°).

⚠️ **Проверка по середине, а не по концам — принципиально.** Сравнение
концов ловило бы только точные дубли, то есть примерно половину
случаев: у второго маршрута концы участка не совпадают ни с чем.

⚠️ **Угловое условие нужно, чтобы не задавить пересечение.** Размер,
который просто пересекает старый под углом (перекрёсток двух трасс),
имеет середину на чужой линии. Молча потерянный нужный размер хуже
лишней линии, поэтому условия два и выполниться должны оба.

⚠️ **Чего правка не ловит:** если новый участок перекрывает старый
размер лишь частично и его середина вышла за пределы старого — размер
нарисуется. Случай возможен, полностью не закрыт.

⚠️ **Геометрия размеров читается из DXF-групп 13 и 14** сущности
`DIMENSION` — ✅ подтверждено живым тестом в консоли: клик по размерной
линии вернул `0=DIMENSION` и две точки в координатах чертежа,
совпадающие с опорами по краям размера.

⚠️ Сканируется **только слой `LEP-DIM`** — чужие размеры с подосновы
глушить свои не должны.

⚠️ **Уже нарисованные дубли правка не убирает** — они лежат на чертеже
обычными объектами. Убрать выделением по слою `LEP-DIM` на общем
участке.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: (1) пролёт маршрута 2 по
общему участку больше не ставит размеры там, где они есть, и печатает
«Пропущено участков…»; (2) на своей улице маршрут 2 размеры ставит;
(3) обычный пролёт на пустом месте работает как раньше, без сообщения;
(4) размер на трассе, **пересекающей** другую под углом, не пропадает.

## ✅ Влившийся маршрут рисовался прямой линией через всё поле (2026-08-05)

**Что было у пользователя.** Маршрут 1 идёт по существующим опорам до
существующей ТП — построился нормально, одна подпись, размеры на месте.
Маршрут 2 начинается на другой улице, потом **вливается** в маршрут 1 и
дальше идёт с ним по общим опорам до той же ТП. Клик по первой опоре
маршрута 2 и по ТП, на вопрос «это Т-образное подключение?» — «Да».
Результат: пролёт нарисован **прямой линией** от первой опоры до ТП,
мимо маршрута.

### Причина — перевёрнутый порядок проверок

Команда решала, что делать, в таком порядке:

1. сравнить `ROUTE` в XDATA обеих кликнутых опор;
2. если разный — спросить «это Т-образное подключение?»;
3. **и только при ответе «Нет»** — посмотреть на геометрию
   (`LEP:FindRoutesThroughPoints`).

Первая опора числится за маршрутом 2, ТП — за маршрутом 1 (её ставили
с ним). XDATA разная → вопрос про Т-образное. И дальше **ни один ответ
не вёл к правильному результату**:

| Ответ | Что происходило |
|---|---|
| **Да** | `IsCrossRoute` → вершины подменяются двумя кликнутыми точками → пролёт рисуется **прямой линией** |
| **Нет** | команда отказывалась работать: «кликните обе опоры одного маршрута» |

При этом маршрут 2 **физически проходит через обе точки**, и геометрия
ответила бы правильно — но её не спрашивали.

Корень в том, что **XDATA решала раньше геометрии**. XDATA помнит, кем
опору *создали*, — навсегда. Геометрия показывает, как трасса лежит на
чертеже *сейчас*. Для влившегося маршрута верна вторая, а спрашивали
первую.

### Как исправлено

Порядок перевёрнут:

1. **Сначала геометрия** — какой маршрут физически проходит через обе
   кликнутые точки. Нашёлся → идём по нему, вопроса нет вообще. Если
   `ROUTE` у опор при этом разный, в консоль идёт пояснение, что пролёт
   пойдёт по трассе, а не по прямой.
2. **Вопрос про Т-образное — только если геометрия ничего не нашла.**
   Это и есть настоящее Т-образное: опора трассы 2 цепляется к опоре
   трассы 1, и маршрута через обе точки на чертеже действительно нет —
   тогда прямая линия верна.
3. **Отказ** — только когда идти реально некуда. В условие добавлено
   «и геометрия ничего не нашла», иначе команда отказывала бы ровно в
   том случае, который эта правка чинит.

⚠️ **Условие работы фикса: полилиния маршрута 2 должна быть проведена
до ТП.** Если её нарисовали только до места слияния, геометрии нечего
находить, и снова появится вопрос про Т-образное. Проверить просто:
включить видимость трасс командой `LEP-ROUTEVIS` и посмотреть, доходит
ли линия маршрута 2 до ТП. Если нет — дочертить.

⚠️ **Отдельная константа тут ни при чём**: допуск поиска
`*LEP-Route-Detect-Tolerance*` = 1 м, и он завышен намеренно — вторую
полилинию рисуют руками поверх стоящих опор.

⚠️ **Провода на общем участке лягут друг на друга.** Сдвиг параллельных
пролётов (`LEP:FindSamePolePairSpans`) ищет совпадение **пары хендлов
опор**. У маршрута 1 пролёт «первая опора → ТП», у маршрута 2 «своя
первая опора → ТП» — пары разные, сдвига не будет, и на общем участке
две линии совпадут геометрически. **Данные при этом разделены
правильно**: у каждого пролёта свой `ROUTE`, своя длина, своя строка
ведомости. Если мешает визуально — это отдельная задача, скажи.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: (1) клик «первая опора
маршрута 2 → ТП» больше не спрашивает про Т-образное и рисует пролёт
**по трассе**; (2) настоящее Т-образное подключение (короткая перемычка
между опорами двух трасс, которые нигде не совпадают) по-прежнему
спрашивает и рисует прямую; (3) обычный пролёт на одной трассе работает
молча, как раньше; (4) в ведомости пролёт числится за маршрутом 2.

## ✅ Пролёт молча привязывался к чужой вершине (2026-08-05)

Найдено при разборе вопроса «второй маршрут вливается в первый у той же
ТП, смогу ли я там тоже кликнуть первую и последнюю опору». Ошибка
оказалась старая и не про массовый клик — просто её раньше не с чем
было столкнуть.

### Механизм

На общем участке провода обоих фидеров висят на **одних и тех же
опорах**. Но опоры эти принадлежат маршруту 1, и вершины при их
установке вставлялись **в полилинию маршрута 1**
(`LEP:InsertVertexOnRoute`). Когда пользователь потом рисует маршрут 2
поверх, у **его** полилинии вершины стоят там, где он кликал мышкой при
рисовании — на опорах маршрута 1 их нет вообще.

Дальше две функции работают с **разной строгостью**, и вся беда в
зазоре между ними:

| Функция | Что меряет | Допуск |
|---|---|---|
| `LEP:FindRoutesThroughPoints` | расстояние до **линии** маршрута | 1 м |
| `LEP:GetNearestVertexIndex` | ближайшая **вершина** | **нет вообще** |

Первая честно находит маршрут 2 кандидатом — линия действительно
проходит рядом с опорой. Вторая молча возвращает ближайшую вершину,
**до которой может быть хоть пятьдесят метров**. Пролёт строился от
неё: длина неверная, а на чертеже линия просто чуть не достаёт до опоры
или проскакивает мимо — заметить почти невозможно.

### Почему это всплыло именно сейчас

Кликая **соседние** опоры, пользователь с большой вероятностью попадал
двумя кликами в одну и ту же вершину маршрута 2 → индексы совпадали →
команда честно говорила «между этими точками нет отдельного участка
маршрута». **Ошибку было видно.** А при клике «первая → последняя»
индексы почти наверняка разные, и ошибка становится полностью
бесшумной. То есть удобная правка того же дня попутно **спрятала бы**
существующий баг — поэтому чинится вместе с ней, но отдельным коммитом.

### Как исправлено

Новая `LEP:EnsureVertexAtPoint` (`LEP-SPAN.LSP`) вызывается для обеих
кликнутых точек перед нарезкой. Три случая:

1. **Вершина на месте** (ближе `*LEP-Span-VertexGap-Tolerance*`, 1 м) —
   обычный случай, ничего не делается. Это 99 % вызовов: символ опоры
   стоит ровно в вершине своего маршрута, расстояние нулевое.
2. **Вершины нет, но линия маршрута проходит рядом** (ближе
   `*LEP-Route-Detect-Tolerance*`) — это и есть «чужая опора на общем
   участке». Вершина **вставляется** той же функцией, что и при
   постановке опоры, в консоль идёт сообщение. Маршрут не
   деформируется: вершина ложится на линию, в точку проекции. Побочная
   польза — следующий пролёт на этой опоре сработает уже без вставки.
3. **Опора далеко и от вершин, и от линии** — значит она вообще не на
   этом маршруте. Догадываться нельзя, любая вставка деформировала бы
   трассу: громкое сообщение с обоими расстояниями, пролёт не строится.

⚠️ **Т-образное подключение проверку не проходит и не должно** — там
«вершины» подставляются искусственно из самих кликнутых точек.

⚠️ Обе точки проверяются **отдельными строками**, а не через `and`:
у `and` вторая проверка не выполнилась бы после первого `nil`, и
пользователь чинил бы проблемы по одной вместо того, чтобы увидеть обе
сразу.

⚠️ `LEP:GetVertices` вызывается **после** проверки, а не до — иначе
работали бы со старым списком, без только что вставленной вершины.

⚠️ Заведена **отдельная** константа `*LEP-Span-VertexGap-Tolerance*`, не
переиспользован `*LEP-Route-Detect-Tolerance*`: вопросы разные
(«проходит ли линия рядом» против «есть ли здесь вершина»), и именно в
разнице между ними жила ошибка. Значения совпадают (1 м), но по разным
причинам.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: (1) обычный пролёт на одном
маршруте строится молча, без новых сообщений; (2) пролёт по маршруту 2
на общем участке даёт сообщение «вершина добавлена» и линия достаёт до
обеих опор; (3) повторный пролёт на той же опоре сообщение уже не
выдаёт; (4) клик по объекту вдалеке от маршрута даёт громкий отказ с
двумя расстояниями и **ничего не рисует**; (5) Т-образное подключение
работает как раньше.

## ✅ Посегментные размеры и у ВЛ — меньше кликов на прямом участке (2026-08-05)

**Вопрос пользователя.** «У меня длинная ВЛ, на ней десяток опор,
прямая как стрела. Сейчас я должен обкликать каждую опору дважды. А
если я укажу первую и последнюю — программа посчитает верно? Может мне
бахнуть целиком?»

**Что выяснилось при разборе кода.** Клик «первая → последняя» и так
считает почти всё правильно, и это не случайность, а следствие
устройства `C:LEP-SPAN`:

- **Длина.** Программа берёт **все вершины трассы между** двумя
  кликами (`LEP:SubList`), а не прямую от опоры до опоры, и суммирует
  путь по ним (`LEP:GetSpanLength`). Десять опор одним кликом дают ту
  же длину, что десять пролётов по отдельности.
- **Ведомость.** Опоры считаются **отдельным сканом блоков** (ЭТАП 2),
  к пролётам отношения не имеют — ни одна промежуточная опора не
  потеряется.
- **Подпись.** Одна на весь участок — ровно то же, что даёт
  автоматическое объединение соседних пролётов.

**Что реально терялось — только размерные линии.** У КЛ размеры с
04.08 рисуются на каждое колено, поэтому у неё клик «первая →
последняя» уже давал те же размеры, что и покликовый. А у ВЛ рисовался
**один** размер по прямой от первой до последней опоры — все пролётные
размеры между соседними опорами исчезали. То есть единственное, ради
чего приходилось дробить прямой участок на пролёты, — это размеры.

**Правка.** Убрано ветвление «КЛ — по коленам, ВЛ — одна линия»: теперь
`LEP:CreateSpanDimensions` работает для обоих. У каждой опоры своя
вершина маршрута (её вставляет `LEP:InsertVertexOnRoute`, и символ
опоры стоит **ровно в вершине**), поэтому участок между каждой парой
соседних опор получает свой размер — независимо от того, кликнул ты
пару опор или весь пролёт целиком.

⚠️ **На обычном покликовом сценарии у ВЛ почти ничего не изменилось**:
у пролёта между соседними опорами список вершин — ровно две точки,
один участок, один размер, как и раньше; точки те же самые. Разница
появится там, где **трасса гнётся между опорами, без опоры на изломе**:
раньше ВЛ рисовала один размер по прямой, то есть меньше, чем провод
реально проходит, — теперь два по коленам. Это исправление, а не
регресс.

⚠️ Переменная `DimDistance` в `C:LEP-SPAN` удалена — она считала прямое
расстояние специально для старой одиночной ветки ВЛ и стала мёртвой.
`LEP:CreateSpanDimension` (ед. ч.) **не удалена** и удалять её нельзя:
она стала «кирпичом», который в цикле дёргает
`LEP:CreateSpanDimensions`.

### Когда бахать целиком НЕЛЬЗЯ

- **ГНБ.** С 03.08 действует правило «один прокол = один пролёт ГНБ», и
  запасные трубы считаются по числу пролётов. Кликнешь кабельный
  участок целиком — получишь **одну** запасную трубу вместо
  нескольких. Проколы кликать по отдельности, как и раньше.
- **Общий участок двух маршрутов.** См. следующий раздел — там сдвиг
  параллельных проводов работает по совпадению **пары** хендлов опор.
  Если маршрут 1 кликали попарно, а маршрут 2 бахнули целиком, пары не
  совпадут и два провода лягут точно друг на друга.
- **Если на участке меняется марка или статус.** Очевидно, но стоит
  записать: пролёт — это один набор данных на всю длину.

### Побочный эффект в плюс

В XDATA длина округляется у **каждого** пролёта, а ведомость складывает
уже округлённое. Десять пролётов — десять округлений вверх, один
большой — одно. На десяти опорах ведомость станет метров на пять
точнее (меньше, но вернее).

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: (1) обычный пролёт ВЛ между
соседними опорами выглядит как раньше — ровно один размер; (2) клик
«первая → последняя» на прямом участке из нескольких опор даёт размер
между каждой парой; (3) длина в выноске и в ведомости у такого участка
сходится с суммой отдельных пролётов; (4) у КЛ ничего не изменилось;
(5) параллельные провода на одной паре опор по-прежнему дают **один**
комплект размеров, а не два.

## ✅ Единое правило округления длин (2026-08-05)

**Что нашёл пользователь.** На живом чертеже один и тот же пролёт был
подписан **двумя разными числами**: выноска ГНБ говорила «L=47 м», а
размерная линия рядом — «46 м». Свойства AutoCAD показывали настоящую
длину 46,4958 м. Оба числа программа посчитала правильно — просто по
двум разным правилам.

**Откуда взялись два правила.** Они появились в разное время и в
разных местах кода, и никто их между собой не сверял:

| Место | Было | Что считает |
|---|---|---|
| `LEP:GetRealLength` | `LEP:RoundUp` (вверх) | длина в ведомость |
| `LEP:FinalizeSpanLabel` | `LEP:RoundUp` (вверх) | длина в выноске |
| `LEP:CreateSpanDimensions` | `LEP:RoundNearest` (математика) | колена траншеи |
| `C:LEP-SPAN` | `LEP:RoundNearest` (математика) | размер пролёта ВЛ |

Логика у каждого была своя и по-своему разумная: длина материала —
это закупка, вниз округлять нельзя, не хватит на монтаже; размер на
чертеже — это геометрия для человека, округляем как в жизни. Беда в
том, что **обе величины видны на чертеже одновременно и рядом**, и
человек читает их как одно число, а не как «материал» и «геометрию».

**Новое правило (решение пользователя).**

```
длина БОЛЬШЕ порога  -> округляем ВВЕРХ
длина МЕНЬШЕ порога  -> по обычным правилам математики
```

Порог — `*LEP-Round-UpThreshold*` = **5,0 м** (`LEP-CONFIG.LSP`).
Со 2026-08-11 у верхней половины правила есть ещё допуск
`*LEP-Round-UpTolerance*` = 0,10 м — см. следующий подраздел.

Зачем нижняя половина правила: просто «всегда вверх» на коротких
длинах врёт в разы. 1,1 м превратился бы в «2 м» — почти вдвое, и на
чертеже это читается как ошибка черчения, а не как запас. Особенно
важно стало с 2026-08-04, когда у траншеи появились размеры на каждое
колено: колена бывают совсем короткие.

**Реализация.** Одна функция `LEP:RoundLength` (`LEP-UTILS.LSP`),
через неё проходят ВСЕ четыре места из таблицы. Раньше каждое место
решало само — теперь решение одно и лежит в одном файле.

⚠️ **`LEP:RoundUp` и `LEP:RoundNearest` НЕ удалены** и удалять их
нельзя:
- `LEP:RoundUp` считает **штуки труб** на ГНБ-прокол
  (`LEP-REPORT.LSP`, ЭТАП 1.7). Полтрубы не купишь — там потолок
  обязателен всегда, никаких порогов;
- `LEP:RoundNearest` работает страховкой от накопленной погрешности
  при суммировании уже целых чисел (`LEP:WriteMasterListBlock`),
  чтобы 45.0000001 не обрезался в 45 не туда.

⚠️ **Разрыва на пороге нет** — проверял специально, пороговые правила
часто его создают. 4,9 → 5; ровно 5,0 → 5; 5,1 → 6. Функция монотонна:
больший вход не может дать меньший выход.

⚠️ **Ведомость тоже подчиняется порогу** — это осознанно. Соблазн
оставить ей отдельное «всегда вверх» был, но тогда мы починили бы одно
расхождение и завели второе: выноска «7 м», а строка CSV «8 м» на том
же пролёте — ровно то, из-за чего правка и делалась. Цена: пролёт
короче 5 м может уйти в ведомости вниз, максимум на 0,5 м. На практике
почти не встречается — до округления к сырой длине уже прибавлены
проценты запаса (ВЛ 4,5 %, КЛ 2–4 %), и они сами перекидывают число
через целое.

⚠️ **Уже начерченное задним числом не пересчитывается** — длины лежат
в XDATA пролётов. Чтобы старый пролёт получил новое округление, его
надо перечертить.

⚠️ **Взаимодействие с нулевым запасом КЛ.** В тот же день пользователь
обнулил `*LEP-KL-Reserve-Pole*` (по просьбе коллеги — «на чертеже хочу
видеть длины без запаса», причину коллега не пояснил). Побочный эффект в
плюс: подпись КЛ теперь показывает чистую геометрию, и сумма размеров
по коленам сходится с выноской точнее, чем раньше. Побочный эффект в
минус: короткие пролёты КЛ раньше всегда перепрыгивали порог за счёт
+6 м, а теперь могут оказаться под ним.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: пролёт ~46,5 м даёт **47**
и в выноске, и в размерной линии (было 47 и 46); короткое колено
траншеи 1,1 м подписано «1 м», а не «2 м»; строка в CSV сходится с
выноской на том же пролёте; строка «Труба для ГНБ-прокола» в ведомости
НЕ изменилась (там своё округление, порога быть не должно).

### ✅ Допуск перед округлением вверх (2026-08-11)

**Что нашёл пользователь.** Размерная линия со свойством
`Measurement = 50,0025` была подписана **«51 м»**. Формально верно —
50,0025 больше порога, значит потолок, значит 51. По сути — чушь:
лишний метр вырос из **двух с половиной миллиметров**, которые взялись
не из трассы, а из того, что точка ставилась мышкой по подоснове.
Запас материала так не считают, а на чертеже это читается как ошибка.

**Что сделано.** У верхней половины правила появился допуск
`*LEP-Round-UpTolerance*` = **0,10 м** (решение пользователя): перед
потолком из длины вычитается допуск, то есть хвост **не больше 10 см**
считается нулём и число вверх не поднимает.

```
50,0025 -> 50   (было 51)
50,09   -> 50
50,10   -> 50   ровно допуск - ещё не поднимает
50,11   -> 51
46,4958 -> 47   хвост настоящий, почти полметра - как и раньше
```

Почему именно 10 см: это заведомо меньше точности, с которой вообще
ставится точка на подоснове. Отбрасывается не материал, а погрешность
клика. Цена в ведомости — максимум 10 см на позицию, против метра
завышения на каждом пролёте, где хвост чуть больше нуля.

⚠️ Ниже порога допуск не применяется — там работает обычная
математика, она вверх без причины и не поднимает.

⚠️ **Монотонность и отсутствие разрыва проверены заново** после
правки, шагом 1 мм на диапазоне 0–2000 м: 4,9 → 5; ровно 5,0 → 5;
5,05 → 5; 5,11 → 6; целые числа остаются собой (50,0 → 50). Ни одного
случая, где больший вход даёт меньший выход.

⚠️ **Старые размеры и подписи не пересчитываются** — перечертить.

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить: тот самый размер 50,0025
подписан **«50 м»**; пролёт ~46,5 м по-прежнему даёт **47**; строка
CSV сходится с выноской; «Труба для ГНБ-прокола» не изменилась.

## ✅ Котлованы ГНБ ставятся сами (2026-08-11)

**Что просил пользователь.** У любого ГНБ-прокола в реальности всегда
есть **рабочий котлован** (там стоит буровая установка) и **приёмный**
(там бур выходит наружу). На чертежах их рисовали руками. Просьба —
ставить автоматически по концам каждой проектируемой КЛ, проложенной
ГНБ. Размер, цвет и вид сняты с его же чертежа.

Два условия, которые он назвал сразу:

1. если по одному маршруту рядом идут **несколько параллельных**
   ГНБ-кабелей — котлован всё равно **один**;
2. в точке, где прокол **меняет направление**, тоже нужен **один**
   котлован, а не два.

### Главное решение: котлован — свойство УЗЛА, а не пролёта

Оба условия оказались одним и тем же правилом. Котлован принадлежит
**концевому блоку** (опоре, КТП, киоску, маркеру смены прокладки), а не
проколу, который в него упирается:

- параллельные кабели висят на **тех же самых** концевых блоках
  (`POLE1HANDLE`/`POLE2HANDLE` у них совпадают) → узел один → котлован
  один, сколько бы кабелей туда ни пришло;
- в точке смены направления сходятся два прокола, но узел (маркер
  `TRANS`) опять же один → котлован один. Физически так и есть:
  буровая переставляется в тот же котлован.

Дедупликация идёт **по хендлу узла** — ключ `HOSTHANDLE` в XDATA
котлована, а не по расстоянию между точками. Сравнение координат с
допуском рано или поздно молча слепило бы два разных котлована в один
или раздвоило бы один — и то, и другое без всяких признаков на чертеже.

### Как это выглядит на чертеже

| Свойство | Значение | Откуда |
|---|---|---|
| форма | замкнутый прямоугольник **2,0 × 1,5 м** | снято с чертежа пользователя: `Area 3.0000`, `Length 7.0000` — это ровно стороны 2,0 и 1,5 |
| ориентация | длинная сторона **вдоль оси прокола** | подтверждено пользователем |
| посадка | центр отступает **2,0 м** от узла **внутрь** прокола | «ставь с отступом от точек, ближе друг к другу, если что я руками подвину»; было 1,5 м, увеличено 2026-08-11 по просьбе пользователя |
| цвет | синий (ACI 5), задан в геометрии блока | со скриншота |
| толщина | `*LEP-LWeight-Proj*` = 0,50 мм | ⚠️ **не** 0,70 мм со скриншота: 0,70 там было у линии подосновы, а котлован чертится как все проектируемые объекты |
| слой | `LEP-PIT`, **печатаемый** | «печатается» |
| подпись | выноска «Рабочий/Приемный котлован» | см. ниже |
| ведомость | **не участвует** | решение пользователя |

### Почему подпись одна на оба типа

Программа не знает и не может знать, с какой стороны прокола реально
встанет буровая — это решает бурильщик на местности, а не геометрия
чертежа. Вариант «спрашивать при каждом проколе» пользователь отверг
(«лучше без доп вопросов»), поэтому ставится общий текст
**«Рабочий/Приемный котлован»**, а лишнее слово стирается вручную при
оформлении.

Промежуточный узел (для одного прокола приёмный, для другого рабочий)
получает подпись **один раз**, вместе с самим котлованом: второй прокол,
пришедший в тот же узел, не добавляет ни котлована, ни второй выноски
(«промежуточный уже будет подписан, добавлять подпись не надо»).

### Отступ — это цель, а не гарантия

Отступ 2,0 м = половина длины котлована (1,0) плюс 1,0 м просвета от
трапеции опоры, которая занимает примерно ±0,5 м поперёк трассы. На
коротком проколе он **автоматически ужимается** (`LEP:PlacePitAtNode`):

- не больше **90% первого сегмента** — иначе на проколе-«молнии»
  (короткий отрезок, потом поворот) центр уехал бы за излом, по
  касательной в чистое поле;
- не больше **трети всей длины** прокола — иначе на проколе в пару
  метров котлованы перепрыгнули бы друг друга, и выноска показывала бы
  на чужой конец.

Ужатие сопровождается сообщением в консоль: молча двигать оформление
нельзя, иначе пользователь будет искать, почему котлован «не там».

### Что появилось в коде

- **`LEP-PITSYM.LSP`** (новый модуль) — блок `LEP-PIT-SYM`
  (`LEP:CreatePitSymbolBlock`) и его вставка с разворотом
  (`LEP:InsertPitSymbol`). Длинная сторона нарисована вдоль оси X блока,
  поэтому угол при вставке — это **прямо азимут прокола, без поправки на
  90°** (ровно на такой поправке уже обжигались в `LEP-END.LSP`, когда
  опоры МТП уезжали перпендикулярно трассе).
- **`LEP-SPAN.LSP`** — `LEP:PitExistsAtNode` (дедупликация по
  `HOSTHANDLE`), `LEP:CreatePitLabel` (выноска), `LEP:PlacePitAtNode`
  (геометрия и XDATA), `LEP:PlaceGnbPits` (оба конца). Вызов — в
  `C:LEP-SPAN` сразу после `LEP:CreateSpanDimensions`, под условием
  `(= Method "GNB")`.
- **`LEP-SETUP.LSP`** — слой `LEP-PIT` (печатаемый, `SetLayerNoPlot`
  сознательно НЕ вызывается).
- **`LEP-CONFIG.LSP`** — раздел «КОТЛОВАНЫ ГНБ».
- **`LEP-START.LSP`** — загрузка модуля (перед `SPAN`) и автосоздание
  блока.

⚠️ **Геометрия считается по `SubVertsRaw`** — несдвинутым вершинам, а не
по сдвинутой на 0,3 м копии провода: параллельный сдвиг это условность
оформления, а котлован копают по настоящей оси прокола. То же правило,
что уже действует для длин и размерных линий.

⚠️ **Отдельной команды у котлованов нет** — ни постановки, ни удаления
(решение пользователя 2026-08-11: «не надо»). Лишний котлован стирается
обычным `ERASE`; ⚠️ **выноска при этом останется** — она отдельный
объект, связь только через `LABELHANDLE` в XDATA (та же схема, что у
опоры с её подписью).

⚠️ **Уже начерченное задним числом не пересчитывается.** ГНБ-пролёты,
нарисованные до 2026-08-11, котлованов не получат — их надо перечертить.
Команды «расставить котлованы по всему чертежу» нет сознательно
(пользователь отказался).

**⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ.** Что проверить:
1. обычный ГНБ-прокол между двумя опорами → **два** котлована, синие,
   вдоль трассы, с отступом внутрь пролёта;
2. второй **параллельный** кабель ГНБ по тем же опорам → **ни одного

4. **траншея котлованов не даёт вообще** — ни одного объекта на слое

| `*LEP-PU-Types*` | виды ПУ **на опоре** (сплит / полукос / не уточнён) |

**2. Чертёж и ведомость разъехались сознательно.** На выноску идёт
короткая метка («ПУ полукос»), в CSV — полная строка («ПУ сплит
прямого включения»). Тот же принцип, что `LEP:GetDisplayLength` /
`LEP:GetRealLength` у пролётов: подписи опор и так двух-трёхстрочные,

**3. Два пункта меню слиты в один — «ПУ на опору».** Опору он
**больше не создаёт вообще**: клик по опоре → навешиваем прибор,
промах → ничего не рисуем и говорим об этом в консоль (прямое решение

## ✅ ПУ не попадал в ведомость: переменная гасила встроенную функцию (2026-08-18)

### Симптом

`LEP-END` → «ПУ на опору» отрабатывал внешне нормально: в подписи опоры
появлялась строка «+ проект. ПУ сплит», прибор на чертеже был. В CSV
после `LEP-REPORT` строки ПУ не было ни одной.

### Причина

Локальная переменная в `LEP:AddEquipToExistingPole` (LEP-DATA.LSP)
называлась `Type`. В AutoLISP имена регистронезависимы, то есть это
**тот же самый символ**, что и встроенная функция `type`, а видимость
локальных переменных — **динамическая**: пока работает эта функция,
`type` хранит строку `"POLE"` и перестаёт быть функцией **во всём, что
из неё вызывается**.

Ниже по цепочке стоит `LEP:SetData` → `LEP:SetDataValueToString`, а там
`(type Value)`. Вызов падал с `bad function`, XDATA не записывалась
ВООБЩЕ, команда обрывалась через `*error*`.

Почему это было не видно:

- строка «+ проект. ПУ ...» дописывается в выноску **до** записи
  XDATA — на чертеже прибор выглядел поставленным;
- сама опора существующая, её собственная XDATA была на месте — из
  ведомости пропадал только прибор;
- сообщение об обрыве команды уходило в консоль одной строкой.

Мина лежала с **2026-07-28**: до этого дня `LEP:SetData` не звала
`type` вообще, и `Type` как имя переменной сходило с рук. В тот день в
`LEP:SetData` добавили страховку по типу значения
(`LEP:SetDataValueToString`) — и функция, написанная ещё 2026-07-16,
начала падать, ничем это не показывая.

### Что исправлено

| Файл | Функция | Было | Стало |
|---|---|---|---|
| `LEP-DATA.LSP` | `LEP:AddEquipToExistingPole` | `Type` | `ObjType` |
| `LEP-DATA.LSP` | `LEP:ReassignPoleRoute` | `Type` | `ObjType` |
| `LEP-DATA.LSP` | `LEP:ReassignSpanRoute` | `Length` | `LengthVal` |
| `LEP-DATA.LSP` | `LEP:SetSpanLabelHandle` | `Length` | `LengthVal` |
| `LEP-PITSYM.LSP` | `LEP:InsertPitSymbol` | `Angle` | `RotAngle` |

Первые две — реально стрелявшие: через `LEP:AddEquipToExistingPole`
идут и «ПУ на опору», и `LEP-POLE-MOVE` (перенос опоры с оборудованием
терял ВСЮ её XDATA), через `LEP:ReassignPoleRoute` — смена маршрута у
опоры. Остальные три пока не стреляли (`length`/`angle` ниже по цепочке
никто не звал), но это заряженные мины, а не безобидные имена.

Весь проект просканирован на такие имена: других совпадений со списком
встроенных функций в списках локальных переменных нет.

### Что это значит для уже начерченного

**Задним числом ПУ не появится.** У прибора, поставленного до этой
правки, XDATA нет вообще — ведомости его брать неоткуда. Нужно навесить
его заново: `LEP-END` → «ПУ на опору» → клик по той же опоре.

⚠️ При повторной постановке строка «+ проект. ПУ ...» допишется в
выноску **второй раз** — лишнюю строку убрать руками (двойной клик по
выноске). Программа не знает, что первая строка уже есть: текста в
XDATA нет, а разбирать чужой текст выноски она не умеет.

### Проверено вживую (2026-08-18)

✅ Главный путь подтверждён пользователем: `LEP-END` → «ПУ на опору» →
`LEP-REPORT` — строка вида ПУ появляется в CSV, команда не обрывается.

Осталось проверить попутно, при случае (эти пути правка тоже задела,
но их отдельно не гоняли):

1. два прибора одного вида — одна строка с количеством 2, разных

2. `LEP-POLE-MOVE` на опоре с ПУ/РЛК: после переноса опора осталась в

## ✅ Смена марки провода/кабеля у готовых пролётов (2026-08-20)

**Проблема пользователя дословно:** «когда уже линия в 500 м размечена
пролётами, а вдруг надо сменить СИП-2 70 мм² на 95».

**Как это выглядело раньше:** никак. Единственный честный путь —
стереть все пролёты и перекликать заново. Отредактировать текст
выноски руками мало: марка живёт в ДВУХ местах — в XDATA пролёта
(`WIRE`/`SECTION`) и в тексте подписи. Правка одного текста дала бы
чертёж с новой маркой и **ведомость со старой**, причём без единого
признака ошибки на экране. Это ровно тот класс тихих ошибок, которых
в проекте и так хватает.

**Стало:** команда `LEP-SPAN-WIRE`.

### Что она меняет и чего НЕ меняет

Меняет ровно `WIRE` + `SECTION` в XDATA и текст подписи. Не меняет:

| Величина | Почему не зависит от марки |
|---|---|
| `LENGTH` / `RAWLENGTH` / `RESERVE` | считаются из геометрии трассы, класса напряжения и способа прокладки (`LEP:GetRealLength`) |
| число фаз (×3 на 10/6 кВ) | от класса напряжения |
| слой, цвет, толщина линии | от класса × статуса × способа прокладки |
| котлованы ГНБ, «+ подъём кабеля по опоре» | от типа прокладки |

Пересчёт длин задним числом сюда сознательно не втащен (решение
пользователя 2026-08-20): «длина от смены провода или кабеля не
поменялась».

**ВЛ ↔ КЛ этой командой не меняются.** Там другой слой, другой способ
прокладки, другие запасы, котлованы и подписи опор — это
перечерчивание, а не смена марки. Список марок-целей берётся ПО ТИПУ
уже нарисованных пролётов, поэтому марка чужого типа в него физически
не попадает.

### Порядок работы

1. **Область действия** — меню: весь чертёж / один маршрут (клик по
   любому его пролёту) / выбор рамкой.
2. **Что меняем** — список марок, которые РЕАЛЬНО есть в выборке, с
   количеством пролётов: `СИП-2 3х70+1х70 мм2  -  пролётов: 14`.
   Список строится по чертежу, а не по конфигу: на старом чертеже
   могут лежать марки из прежних версий `LEP-CONFIG.LSP`, которых в
   текущих списках уже нет, и показать надо то, что есть.
3. **На что меняем** — список из конфига по типу (ВЛ/КЛ) и классу
   напряжения маршрута, тот же самый, что и при создании пролёта.
4. Подтверждение `[Да/Нет]`, дальше замена и пересборка подписей.

### ⚠️ Главная ловушка — объединённые подписи

Подпись общая на группу пролётов одной марки
(`LEP:FinalizeSpanLabel`). Наивное «сменил XDATA у части группы —
позвал Finalize» ломает сразу две вещи:

1. `LEP:FindGroupMembers` собирает группу **по `LABELHANDLE` и марку
   не проверяет** — в новую группу затянуло бы и соседей со СТАРОЙ
   маркой, и они получили бы чужую подпись;
2. те, кого не затянуло, остались бы с `LABELHANDLE` на стёртую
   подпись, то есть вообще без неё (случай, ради которого существует
   `LEP-SPAN-REPAIR`).

Поэтому порядок в команде жёсткий:

1. собрать выбранные пролёты (Targets);
2. добрать **всех** соседей по их текущим группам подписей (Affected) —
   даже тех, чью марку не меняем;
3. стереть старые подписи этих групп и **обнулить `LABELHANDLE`** у
   всех участников — после этого ни одна группа не соберётся по
   устаревшей связи;
4. сменить марку у Targets;
5. пересобрать подписи, вызвав `LEP:FinalizeSpanLabel` по КАЖДОМУ
   участнику Affected.

Звать Finalize подряд по всем безопасно: каждый вызов удаляет подписи
той группы, которую найдёт по АКТУАЛЬНЫМ хендлам, и ставит одну новую.
Цепочка A-B-C сходится за проход — `Finalize(A)` даёт подпись на A+B,
затем `Finalize(C)` подхватывает уже собранную группу через новый
`LABELHANDLE` соседа B и переставляет одну общую на A+B+C. Лишняя
работа есть (выноска создаётся и удаляется несколько раз), лишних
объектов на чертеже не остаётся.

Ради шага 3 пришлось научить `LEP:SetSpanLabelHandle` принимать `nil`
как осмысленное «отвязать от группы»: ключ при этом не пишется вообще
(пустой строкой заменить нельзя — в AutoLISP `""` это ИСТИНА).

### ⚠️ Разные классы напряжения в одной выборке — отказ

Решение пользователя. Списки марок у 10, 6 и 0,4 кВ разные, и молча
положить СИП-2 на десятку — именно та ошибка, которую потом ловят на
объекте, а не на чертеже. Проверка касается только ВЛ: у КЛ список
марок один на все классы, делить там нечего. Смешение ВЛ и КЛ в одной
выборке тоже отклоняется — в норме оно невозможно (марки провода и
кабеля не совпадают текстом), но на битых данных лучше отказаться, чем
положить кабель на воздушный слой.

### Новое в коде

- `LEP:SetSpanWire` (`LEP-DATA.LSP`) — меняет только `WIRE`/`SECTION`,
  остальные поля читает и пишет обратно (`LEP:SetData` перезаписывает
  XDATA целиком, тот же приём, что в `LEP:SetSpanLabelHandle`);
- `LEP:SelectAllSpans` (`LEP-SPAN.LSP`) — набор всех пролётов чертежа
  одним `ssget` по четырём слоям. Тот же `ssget` уже стоял четырьмя
  копиями в файле; старые копии сознательно НЕ переписаны — они
  работают, а трогать рабочий код объединения подписей ради косметики
  значит рисковать на ровном месте.

## ✅ Лишние размеры между вершиной и опорой (2026-08-20)

**Что увидел пользователь:** между двумя опорами размер «30 м», а рядом
с правой опорой — ещё один, «1 м», от опоры до какой-то вершины
полилинии. «Раньше такого не было, но и полилиния была просто прямой».

### Диагноз

Размеры ставятся на КАЖДЫЙ участок между соседними вершинами маршрута
(`LEP:CreateSpanDimensions`, 2026-08-04) — так задумано ради траншеи
«молнией», где надо промерить каждое колено. Пока трасса была прямой,
вершины и опоры совпадали один в один, и вопрос не возникал.

Диагностика по живому чертежу (26 вершин) показала картину:

```
вершина 1: от пред.: 29.25 м   излом: 3.1 град
вершина 2: от пред.:  0.75 м   излом: 0.0 град
вершина 3: от пред.: 29.28 м   излом: 0.9 град
вершина 4: от пред.:  0.72 м   излом: 0.0 град
```

29,25 + 0,75 = 30,00 — шаг опор целый, а вершин две. Таких пар на
чертеже оказалось пять, расстояния 0,13–0,80 м.

**Причина:** угловая опора почти всегда ставится рядом с изломом,
который пользователь нарисовал руками, а снап «это та же самая точка»
в `LEP:InsertVertexOnRoute` — `*LEP-Vertex-Snap-Tolerance*`, **всего
10 см**. Клик мимо излома на полметра — и вставляется вторая вершина
рядом с первой.

### ⚠️ Почему нельзя было решить «в лоб»

- **«Не рисовать участки короче N»** — тогда 0,75 м просто исчезли бы,
  и размер показывал бы 29 вместо 30. Сумма размеров перестала бы
  сходиться с трассой.
- **«Схлопнуть всё, что лежит на прямой» (по углу излома)** — опоры на
  прямом участке ВЛ стоят РОВНО коллинеарно, такой фильтр убил бы все
  размеры между ними, то есть ровно то, ради чего посегментные размеры
  включали для ВЛ 2026-08-05. Вдобавок на живом чертеже паразитные
  вершины давали излом **0,0°**, а соседние с ними настоящие изломы —
  3–4°: по углу их не разделить в принципе.

### Как сделано: схлопывание вершин в узлы

`LEP:CollapseDimVertices` (`LEP-SPAN.LSP`) режет список вершин на
кластеры — всё, что в пределах `*LEP-Dim-NodeGap*` (2 м) от начала
кластера, считается ОДНИМ узлом. От кластера в работу идёт один
представитель:

- у первого кластера — первая вершина, у последнего — последняя (это
  концы пролёта, кликнутые опоры, размер обязан доставать до них);
- у остальных — первая вершина, где РЕАЛЬНО стоит блок
  (`LEP:VertexHasNode`, допуск `*LEP-Dim-NodeSnap*` = 0,3 м), а если
  блока нет ни в одной — просто первая.

Правило «представитель — вершина с блоком» не косметика: без него
размер начинался бы в 0,75 м от опоры, а длины поехали бы (29 / 31
вместо 30 / 30).

`LEP:CollectNodePoints` собирает точки вставки всех узловых блоков
(опоры, МТП, РЛК, КТП, киоски, маркеры) одним `ssget` на вызов.
⚠️ В набор попадают и **откосы** 2-/3-стоечных опор — это блоки на том
же слое. Они стоят в `*LEP-Pole-Sym-Offset*` (2 м) от вершины, то есть
заведомо дальше `*LEP-Dim-NodeSnap*`, и на выбор представителя не
влияют. Именно поэтому NodeSnap нельзя задирать до метра.

⚠️ Схлопнутый список живёт ТОЛЬКО внутри простановки размеров. Длина
пролёта, XDATA и сам провод считаются по полному набору вершин — там
лишняя вершина ничего не портит (сумма отрезков та же).

### Вторая половина: `LEP-ROUTE-CLEAN`

Команда убирает паразитные вершины из самой полилинии. Удаляет вершину,
только если выполнено ВСЁ: в ней нет узлового блока; рядом (ближе
`*LEP-Dim-NodeGap*`) есть вершина, в которой блок стоит; это не первая
и не последняя вершина маршрута. **Одиночный излом трассы без опоры не
трогается** — это настоящий поворот, размер по нему нужен.

⚠️ **Риск, который надо знать:** опоры привязаны к вершинам маршрута
связью `_COincident` (`GEOMCONSTRAINT`). Команда удаляет только вершины
без блока, то есть заведомо не те, за которые кто-то держится, но
список вершин перестраивается целиком через `entmod`, и как решатель
ограничений переживает сдвиг индексов — **живьём не проверено**.
Известно лишь, что обратная операция (вставка вершины в середину тем же
`entmod`) работает годами — на ней держится вся расстановка опор.
Поэтому команда работает с одним маршрутом за раз, показывает список
кандидатов, спрашивает подтверждение и просит проверить после себя.
Не съехало — хорошо; съехало — Ctrl+Z.

Уже нарисованные размеры команда не трогает (общее правило: «уже
начерченное задним числом не пересчитывается») — лишний размер «1 м»
после уборки стирается руками или перечерчиванием пролёта.

### ⚠️ НЕ ПРОВЕРЕНО ВЖИВУЮ (2026-08-20)

- новый пролёт по трассе с парой «излом + опора в 0,75 м»: размер один
  и ровно «30 м», а не «29 м» + «1 м»;
- траншея «молнией» с коленами 3+ м: размер на каждое колено остался;
- прямой участок ВЛ из десятка опор: размеры между КАЖДОЙ парой опор
  на месте (схлопывание их не съело);
- `LEP-ROUTE-CLEAN`: список кандидатов совпадает с тем, что видно
  глазами; после удаления **опоры не съехали** и `GEOMCONSTRAINT` не
  ругается; одиночный поворот трассы остался на месте.

- **Отступ перед текстом подписи (LEADER) — ✅ РЕШЕНО 2026-07-11.**
  Настоящая причина: полка (hookline), которую `LEADER` сам
  пристраивает после наклонного сегмента выноски, имеет длину, равную
  РАЗМЕРУ СТРЕЛКИ (системная переменная `DIMASZ`). У метрического
  размерного стиля ISO-25 по умолчанию `DIMASZ = 2.5` — в нашем
  масштабе (1 ед. = 1 м) это 2,5 МЕТРА полки между изломом и текстом.
  Лечение: `LEP-SETUP` теперь выставляет `DIMASZ` =
  `*LEP-Dim-ArrowSize*` (0,8; настройка в CONFIG) — полка и стрелка
  мельчают, текст прижимается. Подтверждено живым тестом на реальном
  объекте, пользователь выбрал этот вид. Побочно мельчают стрелки
  размерных линий пролётов (`DIMALIGNED`) — сознательно.

  Дорога к решению (сохранено, чтобы не повторять ошибок):
  - `(setvar "DIMGAP" 0)` — не помогло (DIMGAP — лишь малая часть
    зазора, 0,625 против полки 2,5);
  - отключение "хвостика" (`Hookline No`) — не помогло;
  - `LEADER _None` + свой `entmake`-текст — ломало саму линию;
  - гипотеза "внутренние поля рамки MTEXT у TrueType-шрифта" — красиво
    звучала, но ОПРОВЕРГНУТА живым тестом (зазор остался и у
    SHX-шрифта при DIMGAP=0). Урок: полка добавляется только после
    НАКЛОННОГО сегмента (>15° от горизонтали), а первый сравнительный
    тест был с горизонтальными выносками — по построению не мог
    увидеть виновника. Диагональный тест сразу всё показал.
  - Попутно закрыт SHX-вариант шрифта: `isocp.shx` НЕ содержит
    кириллицу — русский текст рисуется уродливым подставным шрифтом.
    `ISOCPEUR` (TrueType) остаётся единственным рабочим вариантом.
  - "На винде такого не было" — там обычно чертят в миллиметрах
    (полка 2,5 мм незаметна), у нас 1 ед. = 1 м. Дело в масштабе
    единиц, не в операционке.

история тестов, найденные группы DXF и обоснование дизайн-решений —
в разделе "✅ Миграция подписей LEADER → MLEADER" в начале файла, эту
запись оставляем только как якорь нумерации списка ниже.

**1. Объединить `LEP-START.LSP` + `LEP-SETUP.LSP` в один файл.**
Проверено: безопасно технически — `C:LEP-SETUP` использует только
`LEP:CreateLayer`/`LEP:CreateTextStyle` (обе туда же переехали бы) и
константы CONFIG, ничего из файлов, которые грузятся позже (ROUTE/
POLE/SPAN и т.д.). Минус — файл станет чуть менее "линейным для
чтения" (функции в середине, а не только последовательность загрузки).
12 → 11 файлов. Пользователю важно именно КОЛИЧЕСТВО файлов в корне.

**2. Один файл для раздачи чертёжникам-коллегам (не разработчикам).**
- Компиляция в `.VLX`/`.FAS` (штатный механизм AutoCAD) —
  **НЕДОСТУПНА на Mac** (подтверждено веб-поиском: Visual LISP
  компилятор есть только в Windows-версии AutoCAD, `.vlx`-файлы на Mac
  даже не загружаются) — не годится, раз разработка/тесты идут на Mac.
- Альтернатива — отдельный скрипт-сборщик (Python, не грузится в
  AutoCAD), который склеивает все `.LSP`-файлы в правильном порядке
  загрузки в один файл для раздачи. Разработка (в чате с Claude)
  остаётся в отдельных файлах как сейчас, склейка — только перед тем,
  как отдать кому-то. Техническая деталь: скрипт должен вырезать
  строки `(LEP:LoadFile "...")` из копии `LEP-START.LSP` при склейке
  (иначе в собранном файле они попытаются найти уже несуществующие
  отдельные файлы и упадут с ошибкой) — тупое склеивание "в лоб" не
  сработает.
- Важно: это ТОЛЬКО про удобство раздачи (один файл вместо тринадцати),
  НЕ про защиту от копирования — большой текстовый файл читается и
  копируется так же легко, как маленькие. Не путать с пунктом 3 ниже.

**3. "Код доступа" / ограничение использования другими людьми без ведома.**
Раз компиляция недоступна (см. пункт 2) — код всегда останется
читаемым текстом, значит ЛЮБАЯ проверка кода доступа будет видна
любому, кто откроет файл в текстовом редакторе (или скормит его ИИ) —
это не настоящая защита, а социальный барьер "на честном слове".
Варианты (от мягкого к жёсткому):
- Ничего не делать.
- Мягкое напоминание при запуске (просто текст "не копировать без
  разрешения"), не блокирует работу.
- Жёсткий код доступа (например, вводить раз в неделю код по
  секретному алгоритму) — реальная преграда для нетехнического
  человека, но: (а) читается в открытую любым, кто откроет файл;
  (б) легитимному коллеге придётся присылать код тоже; (в) риск
  случайно заблокировать самого себя (забыл код/баг в датах).
- То же самое, но с фиксированной датой истечения вместо еженедельного
  кода — меньше рутины, тот же уровень (не)защиты.
Отдельно: если такой механизм будет писать Claude — "известен только
пользователю" не будет буквально верным, Claude тоже будет знать
алгоритм на момент написания; для настоящей секретности нужно после
такого разговора самому поменять секретное число/соль без участия ИИ.
